# 根因分析：多显示器 HDR 拼接（拒绝"放弃式兜底"）

- 日期：2026-09-16
- 触发：用户批评——"问题要研究如何修复，而不是通过放弃避开；去查整体原因"

## 结论先行

我此前为多显示器 HDR 拼接加的"未填充则整图放弃 HDR"兜底，**不是防意外，而是在掩盖一个必然失败**。

追下去发现三个真实根因，均已修复。**这个缺陷同时影响普通的 SDR 多显示器拼接**（不只是 HDR）。

---

## 根因一：D3D11 设备被"切换显示器"销毁 —— 必然失败

`WgcCaptureService.GetOrCreateDevice` 原实现：

```csharp
if (_d3dDevice is not null && _deviceMonitor == hmonitor) { ...复用... }
DisposeDeviceAndNotify();        // ← 换了显示器就销毁
_deviceMonitor = hmonitor;
```

多显示器捕获会为**每个**显示器各建一个会话（遍历所有显示器）。于是：

```
显示器 A：建 deviceA，会话 A 启动（尚未出帧）
显示器 B：判定 _deviceMonitor(A) != B → Dispose deviceA  ← 会话 A 正在用的设备被释放
```

**N 个显示器必然有 N-1 个会话拿到已释放的设备，永远出不了帧**。表现为：首帧超时、`GetLatestSdr()` 恒为 null。

更讽刺的是——创建设备的代码是 `D3D11CreateDevice(DriverType.Hardware)`，**根本没有使用按 hmonitor 查到的那个 adapter**。所谓"按显示器匹配适配器"是空转，每次重建拿到的其实还是同一个默认适配器设备，属于纯破坏性重建。

关于超时值：默认 3000ms，而 WGC 首帧通常 16~50ms。**超时 3 秒不是"慢"，是"根本不会来"**——这本身就是根因的一个症状。

**修复**：只要设备健康就复用（与 hmonitor 无关），仅在设备确实失效（`ImmediateContext` 访问抛异常）时才重建。

## 根因二：取帧失败时把上一帧也清成 null —— 自造的瞬时故障

`ReadBytePixelsPooled` / `ReadFloatPixelsPooled` 在 GPU 锁争用超时（500ms）时返回 null，而发布逻辑无条件执行：

```csharp
_latestSdr = pixels;   // pixels 为 null → 把上一帧也清掉
```

于是一次**瞬时争用**被放大成"这个会话没有帧"，上层随即当成结构性失败。

**修复**：取帧返回 null 时直接 return，**保留上一帧**（宁可用稍旧画面，也好过整块缺失）。

## 根因三：SDR 上转换未乘系统 SDR 白点 —— 亮度基准不一致的真正来源

`BgraToScrgbLinearFast` 输出的是 **1.0 = 80 nits** 的 scRGB。但系统在 HDR 模式下会把 SDR 内容显示到 `GetSdrWhiteLevel()` nits（常见 160~300，本项目默认按 200）。

不乘这个系数，SDR 显示器拼进来的部分会比 HDR 源区域**明显偏暗**——这正是我原本担心、却试图用"放弃整图 HDR"来绕开的那个问题。

**修复**：上转换后按 `sdrWhiteNits / 80` 缩放 RGB（**alpha 不参与缩放**）。

> 注：`GetSdrWhiteLevel()` 内部已做 `SDRWhiteLevel / 1000 * 80` 换算，返回值单位就是 nits。

## 顺带修正：CopyFloatRegion 未夹紧单行宽度

混合 DPI 多屏下 `session.Width`（物理像素）可能大于该屏在逻辑坐标中的剩余宽度，行尾会绕写到下一行开头（错行/撕裂）。已改为按 `min(源行宽, 目标剩余宽)` 拷贝。

---

## 保留的兜底（现在才是真兜底）

"任一显示器未参与填充则放弃整图 HDR"的逻辑**保留**，但语义已变：

- 修复前：它是**必然触发**的，功能等于不存在
- 修复后：三个根因已消除，它只在真正拿不到帧时才生效

半张 HDR（黑洞 + 亮度错乱）确实比整张 SDR 更糟，这个兜底本身是对的——错的是**用它替代了根因排查**。

## 教训

> **兜底逻辑如果"必然触发"，它就不是兜底，而是在掩盖 bug。**
> 加兜底前应该先问：这个分支在正常路径下会发生吗？如果会，那要修的是根因，不是症状。
