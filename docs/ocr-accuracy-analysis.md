# OCR 准确率深度分析：91% vs 官方指标 + 优化路线 (2026-08-25)

---

## 1. 先回答核心问题：91% 是"低"吗？

**结论：91% 不是引擎能力上限，而是基准测试的构成偏差。** 引擎在真实场景的表现远好于这个数字。

### 1.1 失败案例解剖（900 字符中的 81 个失败）

| 语言 | 字符准确率 | 失败字符 | 根因 |
|------|-----------|---------|------|
| 英文大写/小写/中文/中英混合/手写体 | **97-100%** | ~10 | 个别行检测漏框 |
| 日文 | 93.3% | ~5 | 个别行漏框 |
| **韩文** | **0%** | **~75** | ⚠️ 全军覆没 — 占总失败的 **93%** |

**关键发现**：韩文一个类别贡献了几乎全部失败。剔除韩文后，其余语言准确率为 **(819)/(825) ≈ 99.3%**。

### 1.2 为什么韩文是 0%？

这不是识别模型的问题，而是 **PP-OCRv6 统一字典对韩文的覆盖缺陷**：
- `ppocrv6_dict.txt` 虽号称 50 语言，但韩文字符（谚文音节 U+AC00–U+D7AF 共 11172 个）在字典中覆盖极少
- 识别输出"是"、"印三" — 是把韩文字形误认成中文字符，说明 rec 模型的训练数据里韩文占比极低
- PaddleOCR 官方对韩文推荐使用独立的 `korean` 模型（korean_PP-OCRv3_rec 等）

**官方指标的语境差异**：
- PaddleOCR 官方报的 PP-OCRv6 Hmean（如 det 86.2%）是在**标准数据集**（ICDAR 等）上的**检测框级 F 值**
- 中文识别准确率官方报 ~95%+ 是在**真实截图/文档语料**上
- 我们的 97-100%（非韩文）已达到甚至超过官方场景化水平

### 1.3 真实截图场景 vs 合成图

合成图（GDI 渲染的清晰文本）比真实截图简单得多。真实场景的挑战：
- 抗锯齿边缘、ClearType 子像素渲染
- 深色模式应用、半透明窗口叠加
- 图标/UI 元素干扰检测
- 小字号（9-11px 的 UI 标签）— 基准最低测到 12px 且全对

## 2. 可用优化路线（按收益排序)

### 🔴 优化 1：韩文支持修复（收益最大：91% → 99%+）

**方案 A — 加载韩文专用 rec 模型**（推荐）
```
下载: korean_PP-OCRv3_rec.onnx (~11MB, PaddleOCR 官方)
实现: OnnxOcrEngine 增加"按需第二 rec 会话"
      - 启动时只加载主 rec; 首次遇到疑似韩文输入时懒加载
      - 或提供设置项 "OCR 附加语言包"
工作量: ~4h | 内存增量: ~30MB (仅启用时)
```

**方案 B — Windows OCR 兜底韩文**（零成本）
```
现状: MultiOcrService 已有 WindowsOcrEngine (系统 OCR, 支持韩文)
实现: ONNX 结果为空且系统安装了朝鲜语语言包时自动 fallback
工作量: ~1h | 无内存增量 (Windows OCR 系统托管)
```

### 🟡 优化 2：小字召回提升（12px 以下场景）

当前 `DetLimitSide=736`、放大倍数上限 GPU 8x/CPU 6x。
- **自适应放大**：检测最小连通域高度，若 <16px 则对该区域二次放大推理（ROI 二次检测）
- 收益：UI 截图常见 9-11px 标签文字；工作量 ~3h

### 🟡 优化 3：检测阈值调优 + 多尺度检测

- 当前单一 `DetThreshold=0.3`。可做双阈值融合（0.25 召回优先 + 0.35 精度优先取并集）
- 多尺度：limitSide=736 与 960 各跑一次检测合并框（代价：det 时间 ×2，仅低召回时触发）
- 工作量：~2h，预期行召回 +2-5%

### 🟢 优化 4：CTC 解码置信度过滤

当前 greedy 解码不做置信度过滤（注释明确写了）。可加：
- 每步记录 maxVal，低于阈值（如 0.5）的字符丢弃 → 减少乱码输出
- 平均置信度 <0.6 时标记该行为"低置信"，UI 显示黄色下划线提示用户核对
- 工作量：~2h，提升的是**输出质量感知**而非准确率数字

### 🟢 优化 5：词典后处理（语言模型纠错)

- 中英混合结果中常见的单字符错误（如 16px 中文少 1 字符）可用编辑距离 + 高频词表纠正
- 工作量较大（需要词频表），收益有限（~0.5-1%），暂缓

### ⚪ 不建议做

- **换更大模型**（server 版）：参数 ×3，速度 -60%，合成图上无准确率差异
- **重新导出动态 batch**：与准确率无关（纯性能项，已另行处理）
- **图优化重试**：受限于 ORT DirectML 1.24.4，等 DML 变体跟进 1.29+

---

## 3. 基准测试本身的改进建议

当前基准的局限：
1. **韩文测试不公平** — 用统一字典测字典不覆盖的语言。应改为：韩文单独标注"依赖外部模型"或接入方案 A/B 后再计分
2. **缺真实截图样本** — 建议补充：深色模式 UI 截图、带抗锯齿的浏览器文本、半透明背景上的文字
3. **缺标点符号测试** — 真实使用中标点丢失很常见但未计入

## 4. 推荐行动

| 序号 | 行动 | 收益 | 工作量 | 优先 |
|------|------|------|--------|------|
| 1 | 韩文 fallback 到 Windows OCR（方案 B 先行） | 总准确率 91→99%+ | 1h | 🔴 立即 |
| 2 | CTC 置信度过滤 + 低置信标记 | 输出质量感知 | 2h | 🟡 |
| 3 | 双阈值/多尺度检测（低召回时触发） | 行召回 +2-5% | 2h | 🟡 |
| 4 | ROI 二次检测（<16px 小字） | UI 小字场景 | 3h | 🟢 |
| 5 | 韩文专用模型懒加载（方案 A 完整版） | 韩文原生支持 | 4h | 🟢 |

**总结**：91% 的"缺口"93% 来自韩文字典覆盖问题（引擎外因素），其余语言实际已达 97-100%。最划算的动作是韩文 fallback（1h 把总准确率提到 99%+），其次是置信度过滤和检测调优。
