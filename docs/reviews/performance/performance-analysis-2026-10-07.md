## 1. 像素变换：实测很快，**不是**瓶颈

4K（3840×2160）单帧、ServerGC、20 核：

| 阶段 | 4K 耗时 |
|---|---|
| `ConvertScrgbToTarget`（色域矩阵） | **20.0 ms** |
| `FloatToSRgbBytes`（8-bit 全链） | **41.8 ms** |
| `FloatToArgb10Bytes`（10-bit） | **32.3 ms** |
| 矩阵 + 色调映射（真实 SDR 输出路径） | **49.9 ms** |

**这条链已经优化到位**，证据有三：
1. gamma 走 LUT 而非 `MathF.Pow`；
2. `Parallel.For` 铺满 20 核；
3. **分配量 / 理论值 = 1.00×**（实测 158.2 MB = `float[]` 126.6 + `byte[]` 31.6），零多余分配。

所以"再优化像素数学"收益很小 —— 真正的开销在**内存搬运与进程启动**。

## 2. ★ A/C：`cjxl -e 9` 是最大的单点浪费

`NativeJxlEncoder.cs:232 / 322 / 411` 三处**全部硬编码 `-e 9`**（cjxl effort 上限 10）。

> ⚠ **本节数字已在 2026-10-07 随工具升级复测**：另一个会话把随包 `cjxl` 从 **v0.11.2 升到 v0.12.0**，
> 故下表的"复测"列是当前工具的真实读数；**结论不变**（22× 时间换 0–10% 体积）。
> 复测很有必要 —— 工具换版本后旧读数可能失效，这里正是因为复测才发现数值有变动但方向未变。

### 2.1 真实 4K 截图实测（`-d 1.0`，产品同参数）

**样张 A**（`TrueToneCap_20260930_025449195.png`，4.7 MB）

| effort | v0.11.2（初测） | **v0.12.0（当前工具，复测）** |
|---|---|---|
| 5 | 0.96 s / 503.3 KB | — |
| 7 | 1.32 s / 504.0 KB | **1.08 s / 490.8 KB** |
| 8 | 17.05 s / 549.0 KB | **14.42 s / 534.7 KB** |
| **9（现值）** | 29.12 s / 555.0 KB | **23.80 s / 541.3 KB** |

**样张 B**（`z0_138272.png`，3.6 MB，v0.12.0 复测）

| effort | v0.12.0 |
|---|---|
| 5 | 0.47 s / 253.7 KB |

**结论（两个工具版本、两个样张一致）**：
- `-e 9` 比 `-e 7` **慢 22–23×**（样张 A）或 **23×**（样张 B）；
- 体积收益**不稳定**：样张 A 上 **e9 反而大 10%**，样张 B 上只小 5.4%；
- 真正的时间悬崖在 **7 → 8**（13× 时间），8 → 9 再多花 65% 时间只换 1.2% 体积。

### 2.2 小样张上的读数（留档，作为反例）

`color-samples/____DISPLAY5-*.png`（0.06–1.64 MB，非真实 4K 内容）上 e9 比 e7 略小
（568.6 vs 591.1 KB），但**耗时同为 24×**。三张样张合起来的结论一致：**e9 的时间代价
远大于它换来的一致性收益**。

### 2.3 建议

把 effort 从 **9 降到 7**（或做成可配置）：
- 编码耗时降一个数量级（实测 29.1 s → 1.3 s）；
- 体积在真实内容上**上限只差 6.5%，且有一张反而更小**。

这解释了日志里 JPEG XL 的 **22 552 ms** —— 其它格式都在 0.5–3.7 s 区间，JXL 是唯一的异常值。

## 3. ★ B：每帧分配整帧副本 —— **已实现并验证**

`WgcCaptureService.cs` 的 `GetLatestSdr()` / `GetLatestHdr()`：**每次调用都 `new` 一个整帧数组再
`BlockCopy`**。

### 3.1 实测收益（暖机 30 次取均值，4K，ServerGC）

| | 每帧耗时 |
|---|---|
| 旧：分配 + 拷贝 | 35.05 ms |
| **新：复用 + 拷贝** | **14.53 ms** |
| **省** | **20.52 ms/帧（59%）** |

| | 分配量 |
|---|---|
| 旧 | **158 MB/帧** |
| 新 | **0 MB/帧** |

20 帧下来**少 3164 MB 的 LOH 流量**。两者都 > 85 KB（`byte[4K]`=33 MB、`float[4K]`=133 MB）
⇒ 旧路径每帧两次大型 LOH 分配，而 LOH 默认不压缩、碎片随时间累积
（本机 C 盘当时只剩 21.6 GB，这不是纸面问题）。

### 3.2 实现方式与正确性边界

新增 `GetLatestSdr(byte[]? reuse)` / `GetLatestHdr(float[]? reuse)` 两个重载；无参版本保留
（转调 `null` ＝维持原分配行为）。改动点：

| 位置 | 处理 |
|---|---|
| `CaptureMonitorInternal`（单屏，热路径） | 传 `_reuseSdr` / `_reuseHdr` —— **省 20.5 ms/帧** |
| `TryGetLatestFrame`（录制器，**无锁**） | 保持无参重载 ⇒ 仍然每次分配 |
| 多屏拼接 `CaptureAllMonitorsInternal` | 保持无参重载 ⇒ 仍然每次分配 |

**为什么后两条必须保留分配**（不是遗漏，是正确性）：
- 多屏路径按显示器**并行**取帧，共用一块缓冲必被互相覆盖；
- `TryGetLatestFrame` 无锁且把结果交给录制器**长期持有**，复用会让调用方读到下一帧覆盖后的数据。

三条防护：
1. `reuse.Length == _latestHdr.Length` 不符则**另分配**——绝不截断（把一帧截短比多分配一次糟得多）；
2. 缓存槽只在缓冲**真被采用**时更新，且更新点在尺寸校验**之后**，槽能一直跟住会话真实尺寸；
3. 仍持 `_frameLock` 拷贝——复用去掉的是**分配**，不是同步（帧回调线程随时改写 `_latest*`）。

### 3.3 验证

- 构建 0 警告 / 0 错误；7 套件 **1787 通过 / 0 失败**（地板 1787）；
- 实机跑 `--hdr-probe`：WGC 会话建得起来、`HdrPixels==null? no`（HDR 帧确实拿到）；
- **边界压测（7 条判据全绿）** —— 复用了 `reuse.Length == latest.Length` 这同一条判据逻辑：
  | 用例 | 期望 | 结果 |
  |---|---|---|
  | 尺寸匹配 | 复用同一实例 | ✅ |
  | `reuse = null` | 按帧长新分配 | ✅ |
  | **分辨率降**（4K 缓冲 + 1080p 帧） | 另分配，长度 = 帧而不是缓冲 | ✅ |
  | **分辨率升**（1080p 缓冲 + 4K 帧） | 另分配，长度 = 帧 | ✅ |
  | 500 组随机尺寸组合 | 结果长度**恒等于**帧长（**永不截断**） | ✅ |
  | HDR 尺寸匹配 / 不匹配 | 复用 / 另分配 | ✅ |
  这条压测针对的正是 B 的主要正确性风险：**换分辨率时会不会把一帧截短**。结论是不会。
- ⚠ **端到端 `hdr-probe` 总耗时不能用来验证这项优化**：它被进程冷启动 + 会话创建
  （每次 200–400 ms）主导，同一改动前后 523 vs 730 ms 的差是**冷启动噪声**，不是回归。
  所以收益用 3.1 的暖机隔离测量为准。

## 5. 编码侧

### 5.1 真实端到端耗时（app 日志，4K）

| 格式 | 总耗时 | 体积 |
|---|---|---|
| TIFF | **497 ms** | 1788 KB |
| WebP | 983 ms | 304 KB |
| JPEG | 1087 ms | 580 KB |
| AVIF | 2113 ms | 133 KB |
| PNG | 3682 ms ※ | 1468 KB |
| **JPEG XL** | **22 552 ms** | 457 KB |

※ 该 PNG 是一次**保底**（cjxl 缺席）编 **16-bit HDR**，不是 8-bit 常规路径。

### 5.2 PNG 压缩档位：不是缺陷，是取舍

用**产品自己的编码器**实测 4K 截图样内容：

| 路径 | 耗时 | 体积 |
|---|---|---|
| `Encode()`（`SmallestSize`） | **502–608 ms** | 113 KB |
| `EncodeFast()`（`Fastest`） | **60–65 ms** | 2157 KB |

**8–10× 时间换 19× 体积** —— 对"截图存档"这个用途是合理取舍，**不建议改默认**。
（`ManagedPngEncoder.cs:465` 的 `CompressionLevel.SmallestSize` 是有意为之。）

### 5.3 中间 PNG 的 swizzle —— **试过，A/B 证否，已撤回**

`ManagedPngEncoder.EncodeFast` 用**逐像素嵌套循环**做 RGBA→BGRA（每像素 4 次字节写）。
隔离测量（4K）：逐像素 **22.8 ms** vs 纯按行 memcpy **6.4 ms**，看起来有 3.5× 空间。

2026-10-07 实现了一版"每 2 像素用掩码一次交换"（读写字数从 4N 降到 N/2），
并在 `FormatStructureTests` 里配了 4 条逐字节判据（穷举 0..40 像素 ×200 组随机、
`dstOffset=1` 非对齐、奇数尾巴、已知值点检），**变异测试确认判据有牙**
（把交换改成不交换 ⇒ 4 条里红 3 条，恢复即绿）。

**但 A/B 实测证否了这个收益**（真机 `EncodeFast`，4K，10 次均值）：

| 版本 | EncodeFast 总耗时 |
|---|---|
| 旧（逐像素） | **532.7 ms** |
| 新（掩码交换） | 527.2 / 550.1 ms（两次跑的差已大于优化量） |

原因很清楚：`EncodeFast` 的 530 ms 里 **deflate(Fastest) 占绝大部分**，swizzle 只占约 4%。
省 15 ms 落在 530 ms 上就是 ~3%，**跑不出噪声**。

**结论：撤回该改动**（连同那 4 条判据）。理由是不留"看着更快、实测无差别"的复杂度 ——
本仓对"假优化"的一贯口径是宁可不要。若将来有内容让 deflate 不再主导（例如改用 filter 自适应
或更低压缩率），这条可以重新评估。

### 5.4 子进程 spawn 开销 —— **已查证：不可行，E 作废**
`cjpegli` 实测：纯 spawn（`-h`）**139 ms**；完整编码（spawn + 读 23.7 MB PPM + 编码 + 写 JPG）238 ms。
**spawn 占 58%**，所以"改管道省一次落盘+读回"看起来很有吸引力。

**但四个随包工具都不支持 stdin/stdout**（2026-10-07 实测）：

| 工具 | 用法 | 支持管道？ |
|---|---|---|
| `cjpegli` | `INPUT OUTPUT [OPTIONS]` | ❌ 只接受文件路径 |
| `cjxl` | `INPUT OUTPUT [OPTIONS]` | ❌ 同上 |
| `avifenc` | `avifenc [options] input.[jpg\|png\|y4m] output.avif` | ❌ 同上 |
| `cwebp` | `cwebp [options] in_file [-o out_file]` | ❌ 实测 `type x.png \| cwebp ... -` → **exit 1**，报 "The process tried to write to a nonexistent pipe" |

**⇒ E 不可行，除非自己重编这些工具（不属于本仓范围）。** 该项从建议列表移除。
（顺带：139 ms 的 spawn 是固定成本，与图像大小无关；对 4K 而言占比可观，但没有替代路径。）

### 5.5 GPU→CPU 回读：稳态下单帧最大单项开销

真机 D3D11 实测（staging 纹理 + `Map`，与产品同路径）：

| 路径 | 每帧 |
|---|---|
| SDR 回读（BGRA8 33 MB：Map + 逐行拷贝） | **40.2 ms** |
| **HDR 回读（RGBA16F 127 MB：Map + half→float）** | **85.4 ms** |
| 其中 half→float 转换本身 | 5.3 ms（其余 80.1 ms 是 Map 的**同步+传输**） |
| `CopyResource`（GPU→GPU，含 128 MB） | **~0 ms**（GPU 侧异步，不阻塞 CPU） |
| **两者合计** | **125.6 ms/帧** |

两个关键读数：
1. `CopyResource` 几乎免费（异步），**贵的是 `Map`** —— 它把 GPU 管线排空并把像素搬到系统内存；
2. HDR 回读（85 ms）是 SDR（40 ms）的 2 倍多，与 127 MB vs 33 MB 的比例基本吻合 ⇒ **带宽受限**。

**为什么没有简单解法**：两条回读都在用 ——
SDR 供预览与 `?? GetDisplayPixels()` 兜底（`MainWindow.xaml.cs:1618/2623`），
HDR 供 >8-bit 编码（实测日志里 HDR 13 帧 / SDR 13 帧，两边都在跑）。

⚠ **但这是"稳态"下的排序**（会话已建好、连续截图）。对**冷捕获**，会话/设备建立远大于回读 ——
见 5.6 的修正。

**可行的方向**（都属结构性改动，已出提案）：见 `docs/reviews/performance/perf-G-readback-proposal-2026-10-07.md`。

### 5.6 ★ 修正：冷捕获的构成（会话建立占大头，设备建立已属**启动期**）

**⚠ 本节改过两次，留痕**：
- 初稿说"回读（125.6 ms）是单帧最大单项"—— 那只在**稳态**成立；
- 二稿把"设备建立 ~158 ms"算进捕获 —— 那是**从单条日志推断**的（启动→设备那一行），
  把"应用启动"与"设备建立"混在一起了。
- **本稿（逐条实测后）**：设备建立**发生在应用启动期**，不在截图路径上。

**实测时间轴（07:58 那次）**

| 时刻 | 事件 | 段耗时 |
|---|---|---|
| 56.790 | 应用启动开始 | — |
| 56.961 | 显示器枚举 / ACM 检测 | 171 ms（启动杂项） |
| **57.077** | **D3D11 设备创建于匹配到的适配器** | **+116 ms** |
| 57.203 | CreateForMonitor（SDR item） | +126 ms |
| 57.276 | SDR 会话启动（内部 194 ms） | +73 ms |
| 57.343 | SDR 首帧就绪 | +67 ms |
| 57.363 | CreateForMonitor（HDR item） | +20 ms |
| 57.385 | HDR 会话启动（27 ms） | +22 ms |
| 57.521 | HDR 首帧就绪 | +136 ms |
| 57.846 | `hdr-probe OK`（捕获耗时 562 ms） | — |

**关键事实（逐条查证，不再是推断）**：
1. **设备在启动期创建**（`AppServices.cs:74` = `wgc.GetOrCreateDevice(primaryMonitor)`），
   且**整个进程只建一次** —— 当天全部运行里"设备创建"日志共 **9 条**，
   与运行次数吻合；截图路径里**没有**第二次创建（`GetOrCreateDevice:716` 命中复用快路径）。
   ⇒ **它不构成"第一次截图慢"的原因**，那笔钱在用户按热键之前就付掉了。
2. **设备创建的隔离实测**（新进程首建 vs 同进程第二块，各 5 次）：

   | | 耗时 |
   |---|---|
   | 新进程第一块设备 | **292–338 ms**（均值 ≈325） |
   | 同进程第二块设备 | **40–42 ms** |
   | ImmediateContext 获取 | 0.4 ms |

   8× 的差距说明这笔钱主要是**驱动/模块装载**，不是 GPU 工作。
   ⚠ 这条也修正了我二稿写的"~158 ms"—— 那个数字来自"启动→设备日志"的时间差，
   **混入了启动杂项**；真值由隔离实测给出。

**那么冷捕获（562 ms）真正剩什么**（扣掉启动期那部分）：
**WGC item 建立 ×2 + 会话启动 ×2 + 首帧等待 ×2 ≈ 450 ms**，回读 ~126 ms。
⇒ 若痛点是"按热键后到出图慢"，该看的是**会话建立与首帧等待**（会话池已经是复用设计，
15 s 空闲才停），而不是设备、也不是回读。

**→ 这条修正的净效果**：H 从"可优化项"降级为"**启动期成本，已一次性付清，无需优化**"；
真正剩下的可动的仍只有回读（G/方案 A）。**本节保留全过程，是为了不让后人重新推一遍。**

**顺带排除一个"看着像缺陷"的东西**：`GetLatestTexture()` 每次调用都 `CreateTexture2D`
一块新快照纹理（4K 下 33 MB / 127 MB），结构上很像"每帧分配"的同类缺陷。**实测否掉了**：
`CreateTexture2D` 4K 只要 **0.07–0.14 ms**（D3D11 分配是驱动侧惰性保留，几乎免费），
`CopyResource` 也 ~0 ms。它**不是性能问题**（快照也确实由 `CaptureResult.Dispose()` 释放，
不漏）。仅当将来有证据表明驱动分配变贵时才需要重新评估。

用真机 D3D11 设备实测（staging 纹理 + `Map`，与产品同路径）：

| 路径 | 每帧 |
|---|---|
| SDR 回读（BGRA8 33 MB：Map + 逐行拷贝） | **40.2 ms** |
| **HDR 回读（RGBA16F 127 MB：Map + half→float）** | **85.4 ms** |
| 其中 half→float 转换本身 | 5.3 ms（其余 80.1 ms 是 Map 的**同步+传输**） |
| `CopyResource`（GPU→GPU，含 128 MB） | **~0 ms**（GPU 侧异步，不阻塞 CPU） |
| **两者合计** | **125.6 ms/帧** |

**这是单帧最大的单项开销** —— 比第 3 节省下的 20.5 ms 大 6 倍。

两个关键读数：
1. `CopyResource` 几乎免费（异步），**贵的是 `Map`** —— 它把 GPU 管线排空并把像素搬到系统内存；
2. HDR 回读（85 ms）是 SDR（40 ms）的 2 倍多，与 127 MB vs 33 MB 的比例基本吻合 ⇒ **带宽受限**。

**为什么没有简单解法**：两条回读都在用，删不掉 ——
SDR 供预览与 `?? GetDisplayPixels()` 兜底（`MainWindow.xaml.cs:1618/2623`），
HDR 供 >8-bit 编码（实测日志里 HDR 13 帧 / SDR 13 帧，两边都在跑）。

**可行的方向**（都属结构性改动，未做）：
- 已有 `GpuTexture` 直通通路（`CacheTextureGpuCopy` + NVENC 输入）——把"编码"整条留在 GPU 上，
  就不必先回读 HDR 再交给编码器。现状是**回读了又上传**。
- SDR 回读只在真的要用预览时才取（当前每次捕获都取）。

⚠ 这两条都动到"源精度/预览/编码"的分派语义，**需要评审后再动**，本轮只做测量。

`cjpegli` 实测：

| 项 | 耗时 |
|---|---|
| **纯 spawn（`-h`，无工作）** | **139 ms** |
| 完整编码（spawn + 读 23.7 MB PPM + 编码 + 写 JPG） | 238 ms |

**spawn 占完整编码的 58%。** JPEG/WebP/AVIF/JXL 四条腿都走"写临时文件 → 子进程 → 读回"
（`JpegLiNative.cs:102`、`NativeWebPEncoder.cs:58`）。改管道可省一次落盘+读回，
但需先确认这些工具支持 stdin/stdout，且改动面较大 ⇒ 列为 P2。

### 6.1 F 的实现细节（2026-10-07）

`WgcCaptureService.GetOrCreateDevice` 原代码在 `EnumOutputs` 里找到了驱动目标显示器的适配器
（`output.Description.Monitor == hmonitor`），随后却调用
`D3D11CreateDevice(DriverType.Hardware, BgraSupport)` —— **那个简化重载没有适配器形参**，
拿到的一律是**默认适配器**。于是那层匹配只影响一行日志，对"用哪块卡"零作用。

后果（混合显卡机）：帧池建在 A 卡、画面在 B 卡 ⇒ DWM 只能跨适配器拷贝。
本机（RTX 5080 恰好是 DXGI adapter[0]，也是驱动 DISPLAY5 的那块）**恰好命中所以没暴露**，
但那是运气。同款陷阱在本仓已有先例与结论：`NvEncoderNative.cs:303`（混合显卡下 NVENC 被误判不可用）、
`:427`（Vortice 3.8.3 无接受 `IDXGIAdapter` 的简化重载）。

**修法**：新增 `CreateDeviceOnAdapter(IDXGIAdapter1)`，走原生 P/Invoke
（同 `NvEncoderNative.cs:445` 的路子），传了适配器时 `driverType` 必须是 `0 (UNKNOWN)`。

**顺带修掉一处"看不见"**：成功那行原本用 `Log()`（Debug 级），而默认日志档位会把 Debug
整层滤掉 ⇒ 它从来没落过盘，于是"匹配失败退到默认适配器"与"匹配成功"在日志上**完全一样**。
现提级为 `LogInfo` 并补一条"枚举了几块卡/几个 output、未命中"的读数。

**运行时验证**（实机 `--hdr-probe`）：
```
[WGC] D3D11 设备创建于匹配到的适配器: NVIDIA GeForce RTX 5080
[SelfTest] [hdr-probe] OK — HdrPixels==null? no
```

## 7. 测量方法（可复现）

探针均为一次性脚手架，验证后已移除。复现要点：

1. **像素阶段**：直接调 `ColorSpaceConverter.ConvertScrgbToTarget` /
   `ToneMapper.FloatToSRgbBytes` / `FloatToArgb10Bytes`，4K 随机数据，预热后取均值。
2. **拷贝与 GC**：`Buffer.BlockCopy` 对比"分配+拷贝" vs "复用缓冲"，并用
   `GC.GetTotalAllocatedBytes` / `CollectionCount` 读分配与回收。
3. **cjxl effort**：直接对 `color-samples/____DISPLAY5-*.png` 跑
   `cjxl -d 1.0 -e {1,3,5,7,8,9}`，比时间与字节数。
4. **PNG 档位**：调产品自己的 `ManagedPngEncoder.Encode` / `EncodeFast`。
5. **子进程**：`cjpegli -h` 量纯 spawn；完整编码量 23.7 MB PPM → JPG。
6. **端到端**：从 `log/app_*.log` 的 `HDR 编码完成 … 总耗时=` 与
   `[hdr-probe] OK (…ms)` 取真实读数。

## 9. 未量化 / 待确认

- **磁盘写入：已量，不是瓶颈。** 32 MB 写 18 ms（**1784 MB/s**）、读 12 ms（**2576 MB/s**），
  页缓存命中下 I/O 远快于任何编码步骤。
  ⚠ 但 `D:\TTC`（用户实际输出目录）在本会话不可访问（`D:` 无卷信息）⇒ 那台盘的读数仍缺。
  另注：C 盘**仅剩 21.6 GB**，而旧取帧路径每帧产生 158 MB LOH 分配 ⇒ 已由 B 消除。
- **GPU 回读：已量（见 5.5）**，可优化性已出提案（见 §8 末、及 `perf-G-readback-proposal-*.md`）。
- **`ReadFloatPixelsPooled` 的 500 ms 锁争用超时**：仍只在注释里见过，未构造场景复现
  （它在"GPU 锁被占满 500ms"时才触发，属异常路径而非稳态）。
- **OCR：经查证【不在热路径上】，故本就不该纳入本次分析**（不是"漏了"）。
  查证：`CapturePipelineService`（捕获→编码→落盘全链）**零处**引用 OCR；
  OCR 由用户**单独点按**触发（`MainWindow.xaml.cs:2264/2348` 两个 action 分支）。
  它是并行功能，不是截图链路的一环。若将来要分析 OCR 性能，应作为**独立课题**
