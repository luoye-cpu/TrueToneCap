# G 项设计提案：减少 GPU→CPU 回读（2026-10-07）

> 状态：**提案，未实现**。本文件只做设计与取舍分析，供评审。
> 依据：`docs/reviews/performance/performance-analysis-2026-10-07.md` §5.5 的真机实测。

---

## 1. 问题（实测数据）

真机 D3D11 实测（staging + `Map`，与产品同路径）：

| 路径 | 每帧 |
|---|---|
| SDR 回读（BGRA8 33 MB） | **40.2 ms** |
| **HDR 回读（RGBA16F 127 MB）** | **85.4 ms** |
| 其中 half→float 转换本身 | 5.3 ms |
| `CopyResource`（含 128 MB，GPU→GPU） | **~0 ms** |
| **合计** | **125.6 ms/帧** |

**贵的是 `Map`**：它要排空 GPU 管线并把像素搬进系统内存（带宽受限）。`CopyResource` 几乎免费
（GPU 侧异步）—— 也就是说**"数据留在显存里"这件事本身不要钱**，是"搬出来"要钱。

对比参照：像素变换全链（矩阵+色调映射+gamma）才 49.9 ms。**回读比它贵 2.5 倍。**

---

## 2. 现状：数据流是"搬出来 → 又搬回去"

```
WGC 帧池 (GPU 纹理, BGRA8 或 RGBA16F)
   ├─ CopyResource → staging ──Map──→ CPU byte[]/float[]     ← 40.2 / 85.4 ms
   │                                    ↓
   │                              色域矩阵 + 色调映射 + gamma（CPU，49.9 ms）
   │                                    ↓
   │                              byte[] 8-bit  ──→ 编码器
   │
   └─ CopyResource → _latestTexture (GPU, 保持原格式)         ← ~0 ms（已有！）
                        ↓
                   GetLatestTexture() → NVENC 直通（仅 AVIF，且仅 SDR）
```

**讽刺之处**：代码**已经**把 GPU 纹理缓存好了（`CacheTextureGpuCopy`，格式与原纹理一致），
但那条通路只服务 **AVIF + NVENC**，而 CPU 回读那条是**所有格式的必经之路**。

---

## 3. 三种可选方案

### 方案 A（**可行，但改法与我初稿不同**）：HDR 分支下不读 SDR

**⚠ 本节改过两次，留痕**：初稿写"SDR 惰性化、兜底能顶替"，随后查证发现兜底根本不会触发；
再查证才定位到**真正的机制**。以下为最终版。

**真正的机制**（`MainWindow.xaml.cs` 逐行查证）：

```
WgcCaptureService.CaptureMonitorInternal   ← SDR 回读(40.2ms) + HDR 回读(85.4ms) 都在这里，无条件
        ↓ 返回 CaptureResult{SdrPixels, HdrPixels}
MainWindow:
  1566  if (actualHdr && captureResult.HdrPixels is not null)
  1570-1614      → EncodeHdrFrameAsync(...)   ← **从不读 SdrPixels**（已逐行确认）
  1616  else
  1618      var sdrPixels = captureResult.SdrPixels ?? GetDisplayPixels();
  1634      → EncodeAndSaveAsync(sdrPixels, ...)  ← SDR 像素**就是被编码的载荷**
```

**结论**：
- 两条分支**互斥**。走 HDR 分支时，那次 40.2 ms 的 SDR 回读**完全白费**（结果被丢掉）；
- 走 SDR 分支时，SDR 像素**是载荷本身**，不是"可省的兜底"；
- 因此 `?? GetDisplayPixels()`（用 HDR 现做 SDR 的那条兜底）**在真实流程里不会触发** ——
  它是防御性代码，不是常态路径。

**正确的改法**：不是"惰性化 SdrPixels"，而是**让捕获层知道这次会不会走 HDR 分支**，
不打算走时就**根本不回读 SDR**。

- **收益**：HDR 分支下省 **40.2 ms/帧**（125.6 ms 的三分之一），且**不需要**任何
  CPU 补偿（因为那份数据本来就被丢弃，不存在"改用 HDR 现做"的替代成本 ——
  我初稿担心的 41.8 ms 补偿**不存在**）。
- **风险**：中。要在"捕获"与"分支判定"之间建立一处契约：
  `WgcCaptureConfig` 加一个"本次是否可能需要 SDR 像素"的输入，或让 `CaptureResult`
  暴露"按需取 SDR"的能力（而判据在 `MainWindow`，属跨层，要设计干净）。
- **语义影响**：**小**（HDR 分支不读 SDR 已是既成事实，只是把回读也省掉）。
- ⚠ **选区截图那条（`StartSelectionCapture`:2106）旁路不同**：它 `CaptureAllMonitorsAsync`
  之后**硬校验** `SdrPixels`，走的是拼接路径 ⇒ 对那条入口不能省。**要做就只做单屏路径。**

**修订后的评价**：A **值得做**，但它不是"顺手改一下"——它需要在捕获层与 UI 分支之间
引入一个新契约。收益 40.2 ms，风险中，**建议排在有明确收益且零契约改动的事项之后**。

### 方案 B（收益最大，风险最高）：HDR 编码整条留 GPU

**观察**：HDR 回读 85.4 ms 是最贵的一块，而它存在的唯一理由是"CPU 侧做色域矩阵+色调映射"。

**改法**：把色域矩阵 + 色调映射 + gamma 写成 GPU shader（像素着色器读 RGBA16F，
输出目标格式），然后**直接把 GPU 纹理交给编码器**（NVENC 已有直通接口）。

- **收益**：省 **85.4 ms** 回读；顺带省 49.9 ms 的 CPU 变换（改成 GPU 并行）。
- **风险**：**高**。① 需要新增 HLSL 与 D3D11 pipeline；② 颜色数学必须与 `ToneMapper`
  **逐位一致**，否则所有颜色判据（本仓有大量）会漂；③ 只有 NVENC/硬件编码器能接，
  软件编码器（avifenc/cjxl/cwebp/cjpegli 全是**子进程**）**必须**有 CPU 像素
  ⇒ 对它们是纯亏损（多做一次 GPU 变换再回读）。
- **语义影响**：**大**。"谁做色调映射"从单一实现变成两套实现（CPU + GPU），
  而本仓的既有纪律恰恰是"同一条链只写一次"（见 `ToneMapToSdr` 的抽取理由）。

### 方案 C（最保守）：只删掉"回读了又上传"

**观察**：AVIF+NVENC 路径现在既要 CPU 像素（走 `EncodeSdrAsync(px,…)`）又要 GPU 纹理。

**改法**：AVIF+NVENC 直接用 GPU 纹理，跳过那条 CPU 回读。

- **收益**：仅对 **AVIF + NVENC + 非 HDR** 生效，约 40 ms。
- **风险**：低。**但覆盖面窄** —— 只帮到一种组合。

## 4. 建议

| 方案 | 收益（实测量级） | 代价 | 建议 |
|---|---|---|---|
| **A** HDR 分支下不读 SDR | **40.2 ms/帧**（单屏路径） | 需在捕获层与 UI 分支间加一处契约；选区截图路径不适用 | **值得做**，但排在零契约改动事项之后 |
| **B** HDR 编码整条留 GPU | **85.4 ms**（最大） | 引入**第二套色调映射实现**；只有硬件编码器能接，子进程编码器反而更慢 | **先立判据，再谈实现** |
| **C** 删掉"回读了又上传" | ~40 ms，仅 AVIF+NVENC | 覆盖面窄 | 可作 A 的附带项 |

**执行顺序建议**：
1. 若要动 B，**第一步是判据不是实现** —— 本仓 `SelfTest` 已有"两帧合成数据"夹具，
   先用它建立"CPU 与 GPU 两条色调映射链逐位一致"的判据；判据绿了再写 shader。
2. A 与 C 可以一起做（同一处数据流），但都不紧急。
3. **A 之前必须先确认一件事**：单屏 HDR 分支在当前默认设置下**是否经常走到**。
   若你的输出格式是 AVIF/PNG/JXL（走浮点链），则 HDR 分支常态成立 ⇒ A 每次都赚 40 ms；
   若常用 JPEG/WebP（恒 SDR）⇒ 那条分支根本不走 HDR，A 无收益。
   **这一条只有你能回答。**

**一般性纪律**：本项是全链路最大开销，也最容易把颜色弄坏。本仓颜色判据极密
（7 套件 1787 条），**任何动到这里的改动都要先有判据**。

## 5. 若采纳 A：需要先回答的问题

0. **★ 你的输出格式是不是 AVIF / PNG / JPEG-XL？**（决定 A 值不值得做）
   - 这三者走浮点链 ⇒ 单屏 HDR 分支**常态成立** ⇒ 每次省 40.2 ms；
   - JPEG / WebP 恒 SDR（容器没有 >8-bit 档）⇒ 走 1616 的 else 分支 ⇒ **A 无收益**。
   ⚠ 本会话无法替你判断真实使用分布（日志里没有可用的入口/格式频次读数）。

1. **契约放在哪一层？** 两个候选：
   - `WgcCaptureConfig` 加"本次是否需要 SDR 像素"输入 —— 缺陷：该入口在 `MainWindow`
     调捕获**之前**就要知道分支结果，而分支依赖 `actualHdr`（WGC 这次到底给没给 Float16），
     **捕获之后才知道** ⇒ 这个方向可能行不通；
   - `CaptureResult` 暴露"按需取 SDR"（惰性）—— 需要把 `PooledSession` 的引用带到 `CaptureResult`，
     并锁定帧号避免"取最新"语义漂到更晚一帧。
   **这是本方案唯一真正的设计难点，值得先想清楚再动手。**

2. **`GetDisplayPixels()` 的兜底要不要保留？** 查证显示它在真实流程里**从不触发**
   （两分支互斥）。保留无害；但若惰性化后它变成"唯一取 SDR 的路径"，就要重新评估它的成本
   （HDR 现做一次 `FloatToSRgbBytes` ≈ 41.8 ms，与省下的 40.2 ms 基本抵消）。

3. **选区截图路径明确不动**（`StartSelectionCapture`:2106 硬校验拼接后的 `SdrPixels`）。
   要在代码里写明"为什么这条不省"，否则后人会以为漏改。
