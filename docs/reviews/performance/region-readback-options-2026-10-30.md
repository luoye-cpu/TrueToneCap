# 「只把选区搬进 CPU」的两条路（2026-10-30，供拍板用）

> 状态：**取舍分析，未动工**。带日期 ⇒ 取证快照，发现错误不回写，纠正在新文件里（`docs/README.md` §一-1）。
> 前驱：`docs/reviews/performance/perf-G-readback-proposal-2026-10-07.md`（G 项设计提案，同一道题）。
> 那一份已经给出**含 `Map` 的真机分解**（下表引用它），本文件只补三件 10-07 之后才有的事实：
> ① 常驻池被读数否证（2026-10-30 `--capture-freshness-probe`）；② CPU 侧缓冲的**契约注释是错的**，
> 真正的兜底是 `MainWindow` 的防重入闸（同日核出，已改注释）；③ GPU 侧同一族事故**已经发生过一次**
> （`GetLatestTexture` 里 2026-09-15 P0-C 那段：返回共享引用 ⇒ 下一帧 `CopyResource` 在调用方仍持有
> 时原地覆盖 ⇒ 编码期间画面撕裂；修法是"返回即转移所有权"的独立快照）。

范围：一次截图里那两整屏 GPU→CPU 搬运能不能去掉。本文件只做取舍陈述，**不是实施计划**，
里面没有任何一条被批准动工。所有行号是 2026-10-30 工作树现状，代码一动就可能漂。

术语：**整屏搬运** = 一次把 3840×2160 的桌面表面从显存 Map 进托管数组，本机 8-bit SDR 那份
33.2 MB、Float16 转成 float[] 后那份 132.7 MB。**选区** = 用户在预览窗里框出来的那块矩形。

## 判词

**今天不能像补丁那样把 SDR 那一趟省掉，也不能在捕获时就只搬选区。** 三个理由各自独立成立：

1. **选区在捕获之后才存在。** 按下热键只有整屏；矩形要等预览窗关闭才交回来
   （`MainWindow.xaml.cs:2339` 的 `await tcs.Task` 之后才有 `rx/ry/rw/rh`）。"捕获时只回读选区"
   在现架构里没有对象可读。
2. **保存同时需要两份像素。** 选区确定后从两份整帧各裁一次（`MainWindow.xaml.cs:2351` 的
   `ExtractHdrRegionFromDesktop` 与紧随其后的 `ExtractRegionFromDesktop`），用哪一份取决于本次输出
   设置 ⇒ 只要还想保留 8-bit 产物这条腿，就得有一张 8-bit 的整帧可选。
3. **预览拿着这一份拿几十秒。** `MainWindow.xaml.cs:2303/2332` 把 `HdrPixels` 原样交给
   `HdrCaptureWindow.LoadFrame`，后者把它存进 `_frame`（`HdrCaptureWindow.cs:659`），渲染线程每拍
   重读，直到用户框选完成。所以"谁拥有这块缓冲"是这条路绕不开的题，不是实现细节。

**已经量过的部分**：**每帧**的回读分解（G 项 2026-10-07 真机，与产品同路径 staging + `Map`）——
SDR 那趟 **40.2 ms**、HDR 那趟 **85.4 ms**（其中 half→float 只有 5.3 ms）、`CopyResource`（GPU→GPU，含 128 MB）
**≈0 ms**、合计 **125.6 ms/帧**；同一次测量里整条像素变换链（矩阵+色调映射+gamma）才 49.9 ms，
**回读比它贵 2.5 倍**。这一组数给出的关键形状是：**数据留在显存里本身不要钱，是"搬出来"要钱** ⇒
路线 B 的立足点，比路线 A 的"少搬一趟"更根本。
另有 2026-10-30 的 `--capture-freshness-probe`：一次捕获 p50≈300ms，大头就是这两趟搬运
（`artifacts/capture_freshness_2026-10-30.log`）；而"常驻池直接取缓存帧"要拿 250–500ms 的画面滞后
换约 100ms，已判不做。**下面两条路各自能去掉哪一趟，本文件不写"预计省 X ms"**——
上面这些是别的日子、别的机器状态下量的，套到今天的改动上要重新量。

## 路线 A：让 8-bit 产物也从 HDR 帧出，于是 SDR 整屏不再搬

**做法**：`WgcCaptureService.cs:1436/1442` 那两处无条件 `GetLatestSdr(_reuseSdr)` 改成按需——
Float16 那份到货且被采用时不再回读 8-bit；需要 8-bit 的地方（编码、剪贴板、识字、贴图）从
`HdrPixels` 下变换得到。

**要动的契约**（逐条都在生产路径上）：

- `HdrCaptureWindow` 的 SDR 呈现腿。今天 8-bit 屏走 `PixelOps.BgraToScrgbForDisplay`，那条函数负责
  两件事：**参考白/白点**与 **alpha 恒写 1**（口径唯一出处见 `HdrCaptureWindow.CreateOverlayDesc` 的
  注释，背景是"普通屏上 DWM 对 FP16 scRGB 做数值钳位，乘了就把白削成一团白"）。改完之后这一刀
  的输入变成 Float16 场景参考数据 ⇒ 纸白、`SDR白点`、`呈现缩放` 三个读数得重算一遍口径。
  ⚠ 本机已经吃过一次教训：`--sdr-semantics-probe` 实测 8-bit 会话＝authored sRGB（bit-exact），
  当年那条"兜底会双重提亮"的假设就是被它否证的。⇒ 语义必须实测，不能推导。
- `MainWindow.xaml.cs:2244-2254` 那道"SDR 尺寸不合就判桌面捕获数据无效"的闸门要重写：SDR 可能压根不在了。
- 多屏拼接（`WgcCaptureService.cs` 的 `CaptureAllMonitorsAsync`）今天每屏取两份再拷进画布；
  8-bit 画布的来源也要跟着换。
- 会话能力不足时（`CanDeliverExtendedRange` 为假、或该屏在"连续空帧"软冷却里）根本没有 Float16 那份 ⇒
  必须留完整的 SDR 回退，这条腿不能删。

**风险落在哪**：全在**像素语义**上。而这正是维护者 2026-09-22 已经拍板的口径——"源精度按显示器能力"
三档（sRGB 屏→8-bit SDR / 广色域→BT.2020+SDR / HDR→Float16）。路线 A 不是执行这条口径，是**改写它**，
所以只有维护者本人能定；任何 agent 在本仓文档里留下的"维护者裁决"字样都不算授权。

**能用的判据**：`--selftest` 的 `HDR_JUDGE`/`HDR_SOURCE` 判的是"下游拿到的精度是否真的高于 8-bit"，
判不了"8-bit 产物与今天是否同一张画面"。后者需要**逐字节对撞**：同一帧源，分别走旧路（SDR 整屏→裁）
与新路（HDR 整屏→下变换→裁），比两份 8-bit 区域字节。这台对撞目前**不存在**，是路线 A 的前置件。

## 路线 B：预览与编码都吃 GPU 快照，只有选区在框选结束后回读

**做法**：帧不进 CPU。会话侧本来就有每帧的 GPU 快照（`GetLatestTexture()`，GPU→GPU 拷贝），
预览合成也早就是纹理采样（`Shaders/OverlayComposite.hlsl`）——缺的是**把快照交给预览窗**这条路，
以及"框选结束→只回读那块矩形"。

**挡路的事实（三条都不是小工）**：

1. **两个设备各自独立。** 捕获侧自己 `D3D11CreateDevice`（`WgcCaptureService.cs:991`，注释说明为什么
   要挑适配器），预览窗为了自己的交换链又 new 了一个（`HdrCaptureWindow.cs:438`，设备丢失/重建路径
   在 `:900`）。全仓 `src/TrueToneCap.App` 与 `src/TrueToneCap.Core` 搜 `ResourceOptionFlags.Shared`、
   `OpenSharedResource`、`SharedHandle`：**零命中** ⇒ 跨设备共享要么新写，要么把两处的设备合并成一个
   ——后者牵交换链创建、适配器选择、设备丢失重建、`_d3dContextLock`/`_gpuLock` 两把锁的分工，
   是本仓最容易出"复现不出来的花屏/越界"的那一族。
2. **快照会被下一帧覆盖——CPU 与 GPU 两侧同一个坑，GPU 侧已经栽过一次。**
   CPU 侧：`WgcCaptureService.cs:338` 那一行 `_writeBufferHdr = _latestHdr;` 说的是"刚交出去的那块
   立刻降级成下一帧的写入缓冲"；把它护住的是 `CopyHdr`（`:495-498`）那趟 132.7 MB 的 `BlockCopy`，
   代价本机实测 **13.4 ms**（孤立项）。GPU 侧：`GetLatestTexture`（`:632`）的注释记着原委——
   2026-09-15 P0-C 之前返回的是**缓存纹理的共享引用**，下一帧 `CacheTextureGpuCopy` 的 `CopyResource`
   会在调用方仍持有引用时原地覆盖其内容，**实机表现为编码期间画面撕裂**；修法是"在 GPU 锁内
   CopyResource 到一块独立快照后返回该拷贝，返回即转移所有权"。
   ⇒ 路线 B 要做的正是把这条已经付过学费的所有权纪律，从"每次拷一份"升级成"多槽 + 被持有的那代不被覆写"，
   而预览窗跨几十秒持有是它的硬场景（`HdrCaptureWindow.cs:659` 的 `_frame`）。这与另一条欠账
   （#32 去那趟克隆）是**同一个问题**，应当一起设计、一起补仪表，不要分两次改同一段缓冲。
3. **色彩口径搬家。** 今天 Float16→呈现的那一刀在 CPU（见路线 A 那条），HDR 直通只有
   NVENC AVIF 8-bit 一条格式吃到（闸门在 `CapturePipelineService.cs:596-602`：**本次需要色域搬运就
   弃用 GPU 直通**）。纹理直采之后，色域/纸白/alpha 的契约要么进 HLSL，要么在选区回读后再走 CPU 一刀——
   后者意味着编码腿仍然要一张 CPU 区域图（但只是选区大小）。

**收益形状**（不做量化承诺）：它去掉的是"整屏"这一档，路线 A 只去掉"两趟里的一趟"；B 的改动面更大，
且**顺带把 #32 那笔 13.4 ms 的克隆一并解决**（因为所有权纪律是它的硬前提）。

## 两条路之外，一条更小但需要前提的小路

只在**同时满足**"本次 HDR 输出真开着 + 设置要求 ≥10-bit 产物 + 该屏 Float16 会话到货且尺寸相符"时，
才跳过 SDR 整屏回读；任一不成立就照今天。这样不碰任何像素语义（8-bit 那条腿的产物一字不变），
省的是那一档条件下的一次 33.2 MB 搬运。

**前提**：`HdrCaptureWindow` 的 SDR 呈现腿与那道"桌面捕获数据无效"闸门（`MainWindow.xaml.cs:2244`）
必须在"这一张只有 Float16"的情况下仍能成立，因此它仍然是路线 A 的一半工作——只是把风险面收窄到
"HDR 输出开着且要高位深"这一档。量级上限照着 G 项那张表读（SDR 那趟 40.2 ms/帧），**但那是 10-07 的
机器状态**；本机今天的分解没量过。手边只有孤立项（`artifacts/readback_bench_2026-10-30.log`：整帧
half→float 并行 6.0 ms、HDR 132.7 MB BlockCopy 13.4 ms、SDR 33.2 MB 3.3 ms；⚠ 都不含 GPU `Map`，
不许相加解释端到端）。

## 验收方案（不论选哪条，顺序都是这个）

1. **先补那台缺失的仪表**，再动缓冲。今天没有任何一条判据能回答"**已经交出去的那一块，事后有没有被
   后续帧改写**"：`--capture-freshness-probe` 判"截图落后现实多少 ms"（GDI 独立参照 + 两条控制臂），
   `--sdr-semantics-probe` 判"两次读数是同一张画面"，`--preview-ui-probe` 判"屏幕上的呈现结果"，
   `--selftest` 判"源精度"与判据自身是否活着。缺的那台应当是：取一份帧→哈希→让会话继续出帧（画面
   必须在变，否则判据空转）→再哈希同一份数组比对。**并且把 `CopyHdr` 那趟拷贝变异掉时它必须红**——
   红了才证明今天真的是那趟拷贝在护着用户看到的画面。
2. **像素等价**用逐字节对撞：同一源帧、两条腿、比区域产物（路线 A 必做；路线 B 至少要比"选区回读
   出来的那张与今天裁出来的那张"）。
3. **时序纪律**继续用结构锁：本仓已经吃过三次"顺序在产物里看不见"的亏（建池与等首帧的顺序、
   half→float 的并行与 `finally` 里的 `Unmap`、图集排版投递与起渲染线程的顺序），路线 B 的所有权移交
   属同一族，必须锁形状而不是只测耗时。
4. 测试入口不变：禁 `dotnet test`，用 `dotnet run --project src/TrueToneCap.Test -c Release -- --<suite>`
   并确认输出里的 `RESULT suite=... passed=... failed=...` 行。GUI 手验归维护者。
