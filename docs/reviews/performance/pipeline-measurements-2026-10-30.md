# 管线补测结果（2026-10-30）

> 带日期 ⇒ 取证快照，不回写。本文只补 `pipeline-performance-audit-2026-10-30.md` §6 的待量清单，
> 不改任何产品代码；每个数都能指到 `artifacts/` 里的日志。
> 口径：本机单屏 SAC2765 3840×2160（HDR 在线）、RTX 5080、出货目录 Release 二进制 v0.3.7。

## 判词

1. **OCR 的大头是 rec，不是 det**：1200×800 / 14 行，DirectML 端到端中位 **708ms**，
   其中 det 100ms、rec 615ms（87%）；CPU 端到端 2492ms，det 749ms、rec 1733ms（70%）。
   现有 `RecognizeCoreAsync` 是**逐框串行**调 rec ⇒ 下一个可用优化是"合批 rec"，不是换引擎。
2. **PNG 的大头是 deflate，且占比随内容升高**：2250×1350 / 10-bit，
   UI 内容 level 9 总 233ms、deflate 195ms（84%）；噪声内容 level 9 总 4258ms、deflate 4051ms（95%）。
   转换+滤波只有 33–74ms（并行自适应滤波并不慢），**换 deflate 实现/降档是唯一有效杠杆**。
3. **level 8 再次比 level 9 更快且更小**：噪声 4258→509ms（**8.4×**），体积 15988407→15615385 B（−2.3%）；
   UI 233→105ms（2.2×），体积 186789→201207 B（+7.7%）。与 `CompressionEffort.cs` 既有读数同向。
4. **池存活期的 GPU 成本很小**：同一 pid、同一块 3D 引擎，池死 **0.00%**、池活 **1.97%**（avg，max 2.10）；
   动态内容臂同为 1.97% ⇒ 帧交付已被 WGC 限速，动态内容没有把成本推高。
   15s 池寿命内约 **0.3 秒引擎时间**（1.97% × 15s）—— 不构成优化项（见 §5）。
5. **启动内存**：窗口出现时 WorkingSet 365–366MB / Private 421–431MB；OCR 后台加载完 454–457 / 565–569MB；
   静置 60s 不回落（451–457 / 564–567）。一次捕获后 537–667 / 806–929MB，池回收后仍留 516–532 / 756–806MB。
6. **翻译文本路单行 ≈1.09s**（Edge translatetext，n=5，974–1150ms）；14 行按并发 4 分 4 波 ≈4.4s。
   视觉路本机**不可测**：设置里 `LlmEndpoint` 为空、`localhost:4000` 无监听。
7. **跨屏（#46）仍被硬件阻塞**：本机只有一块屏，本轮全部读数都是单屏 4K。

## 1. 方法与工具

新增两个 Tools 入口（只读反射，不改产品代码；签名变了会立刻抛 `MissingMethodException`）：

```
dotnet run --project src/TrueToneCap.Tools -- --perf-ocr <modelDir> [--w 1200 --h 800 --iterations 5]
dotnet run --project src/TrueToneCap.Tools -- --perf-png [--w 2250 --h 1350]
```

- **OCR 臂**：GDI 生成 1200×800 的 UI 样张（标题 + 12 行中英混排 + 6 个色块，共检出 14 框），
  先 warmup 一次，再跑 5 次 `RecognizeAsync` 计时；随后反射 `RunDetection` / `RunRecognition`
  把同一张图拆成 det / rec / 其余（张量拼装与后处理）。
- **PNG 臂**：2250×1350、10-bit 左对齐的两份输入——UI 样张（由 8-bit 扩展）与确定性噪声；
  反射 `BuildRawScanlines16` / `CompressDeflate` 分别计时，再与 `ManagedPngEncoder.Encode16`
  的整次耗时对照；每档格式跑 2–3 次取中位。
- 代码：`src/TrueToneCap.Tools/PerfMeasureBench.cs`；分派在 `FormatBench.cs` 顶部。

## 2. OCR：端到端与 det/rec 分段

出处：`artifacts/perf_ocr_stages_2026-10-30.log`

| 臂 | warmup | 端到端中位 | det 中位 | rec 中位 | 其余 | 框数 |
|---|---|---|---|---|---|---|
| DirectML | 3142ms | **708ms**（670–812） | 100ms（91–110） | **615ms**（595–682） | 0–94ms | 14 |
| CPU | 2583ms | **2492ms**（2358–2557） | 749ms（717–774） | **1733ms**（1701–1804） | 0–90ms | 14 |

5 次原始样本：DML `total=[670,675,725,812,708]`、`det=[103,110,96,100,91]`、`rec=[595,607,615,618,682]`；
CPU `total=[2470,2358,2492,2498,2557]`、`det=[722,717,749,774,766]`、`rec=[1759,1733,1731,1804,1701]`（单位 ms）。

读法：

- 单框 rec ≈ 615/14 ≈ **44ms**（DML），远高于旧文档的"rec 6.6ms/次" —— 后者测的是小文字条，
  这里是 1200px 宽整行。**rec 的成本随裁剪宽度走**，所以"合批 + 控制 rec 输入宽度"才是杠杆。
- det 只占 14–30%，且 DML 已比 CPU 快 7.5×；换 det 模型不在收益面上。
- warmup 的 2.6–3.1s 是一次性加载（启动后台已做过，用户路径不会重复付）。

## 3. PNG 16-bit 保存拆分

出处：`artifacts/perf_png_split_2026-10-30.log`（`raw` 23.2MB，2250×1350×8B）

| 内容 | 档位 | 转换+滤波 | deflate | 整次编码 | 文件 | deflate 占比 |
|---|---|---|---|---|---|---|
| UI | Smallest(9) | 33ms | **195ms** | 233ms | 186,789 B | **84%** |
| UI | Quick(8) | 33ms | 73ms | 105ms | 201,207 B | 70% |
| UI | Fastest(1) | 33ms | 8ms | 37ms | 468,549 B | 22% |
| 噪声 | Smallest(9) | 74ms | **4051ms** | 4258ms | 15,988,407 B | **95%** |
| 噪声 | Quick(8) | 74ms | 409ms | 509ms | 15,615,385 B | 80% |
| 噪声 | Fastest(1) | 74ms | 162ms | 294ms | 20,403,926 B | 55% |

读法：

- **转换+滤波只要 33–74ms**，自适应 5 滤波器 + 并行分带不是瓶颈；全部优化空间在 deflate。
- 噪声臂 4.26s 与今天真实保存 2250×1350 HDR PNG 的最高值 12.75s 同量级（差额在浮点→PQ16 与其它管线段），
  UI 臂 233ms 与低端保存 571ms 同量级 ⇒ 样张的两个内容型覆盖了真实分布的两端。
- level 9→8 在噪声上 **8.4×**、在 UI 上 2.2×；噪声臂上 level 8 体积还小 2.3%。这与
  `CompressionEffort.cs:219-222` 的历史读数一致（那批是 4K/63.3MB，10.4×）。

## 4. 启动内存与池存活期 GPU

出处：`artifacts/perf_pool_mem_20261030b.log`（第一轮 `..._20261030.log` 只盯 `engtype_copy`，读出一片假零；第二轮 `...b` 改成全引擎求和，正控才成立）

| 时刻 | WorkingSet | Private |
|---|---|---|
| 窗口出现（进程到主窗口 953/1029ms） | 365–366MB | 421–431MB |
| +8s（OCR 双引擎后台加载完） | 454–457MB | 565–569MB |
| +60s（静置） | 451–457MB | 564–567MB |
| 一次捕获后 +1s | 537–667MB | 806–929MB |
| 池回收后（捕获 +21s） | 516–532MB | 756–806MB |

GPU（同一 pid，`\GPU Engine(pid_*)\Utilization Percentage`，1s 采样，全引擎求和）：

| 状态 | 全引擎 avg | max | copy 引擎 | 主引擎 |
|---|---|---|---|---|
| 池死·静态 | **0.00%** | 0.00% | 0.00% | — |
| 池活·静态（捕获后 8s） | **1.97%** | 2.10% | 0.00% | eng_0_engtype_3d |
| 池死·静态（再 20s） | 0.00% | 0.00% | 0.00% | — |
| 池活·动态（ffplay testsrc2 4K60 全屏） | **1.97%** | 2.07% | 0.00% | eng_0_engtype_3d |
| 池死·动态后 | 0.00% | 0.00% | 0.00% | — |

读法：

- 正控成立：同一 pid、同一引擎，唯一变量是池状态 —— 池死恒 0.00%，池活恒 1.97%。
- `CopyResource` 在本机记在 **3D 引擎**（copy 引擎恒 0%）⇒ 只盯 `engtype_copy` 会得到假零。
- 动态内容没有把 1.97% 推高：WGC 帧交付本身已被限速，池内那两次整屏拷贝随帧率走，
  不是随"内容变化量"走。
- 15s 池寿命 × 1.97% ≈ **0.3 秒引擎时间**；相对一次 4K 游戏的量级可忽略。
  ⇒ 审查里候选 B（每帧两次整屏拷贝）**按本读数判不做**，除非将来池寿命被拉长。

## 5. 翻译

出处：`artifacts/perf_translate_live_2026-10-30.log`（`TTC_LIVE_TRANSLATE=1 --service-tests`）

- 文本路单行、默认免费链路：**1126 / 996 / 1150 / 1087 / 974ms，中位 1087ms**，
  交出译文的后端 = **Edge (translatetext)**（5/5 一致）。
- 14 行按 `SemaphoreSlim(4)` 分 4 波 ⇒ 纯网络约 **4.4s**（不含 OCR 0.7s）。
- 视觉路：`LlmEndpoint` 为空、`localhost:4000` 无监听 ⇒ **本机不可测**；
  要量必须先把端点填上（会把整图 base64 发出去，属用户配置，未动）。

## 6. 跨屏（#46）

本机只有一块屏（SAC2765，HDR 在线），"每块屏 / 多屏拼接 / 不同 DPI"三项都缺硬件。
本轮所有读数都是**单屏 4K**；跨屏结论不能由本轮外推。

## 7. 对审查结论的修订

| 审查项 | 修订后 |
|---|---|
| 候选 B（池内两次整屏拷贝） | **判不做**：实测池活 1.97% 引擎、池死 0.00%，15s 内约 0.3s 引擎时间 |
| 候选 C（deflate 实现） | **保留并升为首位性能项**：deflate 占编码 84–95%，转换/滤波只有 33–74ms |
| 候选 D（OCR 懒建 CPU） | 保留但降级：启动 +8s 相对 +0s 多 138–144MB，尚不能归因到 CPU 会话（DML 也占） |
| 新增候选 E（OCR rec 合批） | **新增**：rec 占 OCR 端到端 70–87%，现为逐框串行；合批是直接杠杆，收益未量 |
| 翻译视觉路 | 维持"未量"：本机无端点 |
| 跨屏 #46 | 维持"待硬件" |
