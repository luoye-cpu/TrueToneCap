## 0. 先给判词边界

这次审查要回答的不是“之前那个 OCR 修复有没有通过”，而是三个分开的问题：

1. **源码可靠性**：`ec440aa..HEAD` 这 8 个提交里的改动，在异常、边界、并发、性能和隐私上是否站得住？
2. **当前软件可用性**：用户现在拿到的 0.3.20 包，和源码 HEAD 的行为差多少？修复是否已经到用户手里？
3. **发布完整性**：这批发包后改动是否具备进入 0.3.21 的条件；没有的话，缺的是代码、证据、版本还是商店门禁？

三个问题必须分开下结论。**“全量测试通过”不等于“当前包已修复”，也不等于“可以发布”。**

## 2. 初判风险假设（待验证，不是结论）

以下是读 diff 后要重点证伪/证实的假设，按风险排序。每条都必须在 W1/W2 给出 `file:line` 或运行证据。

| # | 假设 | 可能影响 |
|---|---|---|
| H1 | `MergeOrphans` 的 “≤2 字符 / 重叠 ≥0.5 / gap ≤1.5H” 会把彼此无关的短 UI 标签并进段落或按钮文本 | 用户看到错行、错译 |
| H2 | 分栏阈值 `max(2.5H,40px)` 对 12–16px 小字过宽，可能把两个相邻控件并成一行；对大字号又可能切碎同一段 | 预览行数/覆盖不可预测 |
| H3 | `BuildRows` 的 0.60 重叠/中心比例对超高框、旋转框、上下标仍可能吞行或拆行 | 行序错、覆盖框跨行 |
| H4 | `MapDecodedIndices` 把 `dict.Length+1` 硬编码为空格类；换模型/换字典后会误映射或漏空格 | 英文粘连或特殊 token 泄漏 |
| H5 | Windows OCR 混合路径仍用固定 `lineGap=8px` 分行，4K/不同字号下可能切碎中文行 | Windows OCR 用户可用性 |
| H6 | `Text == join(Lines)` 只在 ONNX 路径有真实截图证据；Windows OCR 混合路径/空结果/异常结果未覆盖 | 复制全文与预览不同序 |
| H7 | `TTC_OCR_DUMP_BOXES=1` 会把完整 OCR 文本写到 `%TEMP%`，默认关闭但没有隐私提示/保留期限 | 敏感截图文本落盘 |
| H8 | `IsCjkNoSpace` 仍是 `char` 级，Unicode Extension B 及以上代理对未覆盖 | 极少数汉字的空格/拼接错误 |
| H9 | 新 composer 的 `BuildRows` O(n²) + `MergeOrphans` 多轮 O(n³) 在密集页面可能放大 OCR 延迟 | 4K/多栏页面卡顿 |
| H10 | 0.3.20 包仍是发包前二进制，OCR 修复未进入用户手里的包；`CHANGELOG` 却已有“未发布”条目 | 用户以为已修复，实际没有 |
| H11 | 验收文档的断言数、行数、段落组数可能与当前 HEAD 重跑值漂移 | 发布说明/商店文案失真 |

### W1 — 源码静态审查（逐文件、逐调用链）

按 4 条 lane 并行/串行深读：

1. **Composer 核心**：`OcrLineComposer` 的 Expand → BuildRows → segment → JoinFragments → MergeOrphans → ToOcrLine。
   - 检查坐标归一化、负宽高、空文本、重复框、重叠框、零高度、行锚点漂移。
   - 检查 `IsCjkNoSpace` 的 Unicode 范围、`NormalizeFragment` 的所有空白分支、日文括号/半角假名/扩展 A/B。
   - 检查排序稳定性和确定性；同一输入多次运行文本是否一致。
2. **引擎接入**：`OnnxOcrEngine` 的 `RecognizeCoreAsync`、`MergeDetLines`、`MergeDetLinesLegacy`、`MapDecodedIndices`、`DumpRawBoxes`。
   - 检查 `Text`/`Lines` 同序、legacy 开关、异常/空结果、模型加载失败、批处理边界、取消。
   - 检查尾随空格类映射的模型契约：实际 `numClasses`、字典长度、低置信度、重复字符。
3. **Windows OCR 路径**：`OcrService.RunMixedLanguageOcrAsync` + `ComposeWindowsLine`。
   - 检查 `lineGap=8` 分行、Y 抖动、词框并集、中文逐词空格、空词表、语言包缺失。
4. **App/翻译侧**：`OcrPreviewWindow.CurrentFullText`、预览覆盖使用 `Lines`/`Words` 的位置、翻译段落分组入口。
   - 检查有译文/无译文、空行、行数变化、复制全文、选区高亮、覆盖框越界/重叠。

**W1 出口**：每个 changed file 都有审查记录；候选缺陷必须带 `file:line`、触发构造、用户可见性、P 级、T 级。

### W2 — 行为与边界验证

#### W2.1 纯函数/属性测试

- 对 `OcrLineComposer` 输入随机框（0–2000 个、宽高 0–300、坐标含负值/重叠/重复），断言：
  - 不抛异常、不死循环（超时上限）；
  - 输出 `Text` 与 `Lines` 文本逐行一致；
  - 输出行框在输入框并集内、非负；
  - 同输入多次运行顺序/文本一致；
  - 空输入、单框、全空白、全重叠框安全。
- 对阈值做边界扫描：重叠 0.59/0.60/0.61、中心差 0.59/0.60/0.61、gap 2.39H/2.40H/2.50H/40px 边界、orphan gap 1.49/1.50/1.51H。
- Unicode：汉字、平假名、片假名、半角假名、CJK 标点、日文括号、兼容表意、Extension B 代理对、NBSP/U+3000、emoji、全角拉丁。
- 确定性：同一候选集合不同插入顺序，输出应不受影响（除非设计明确按输入顺序）。

#### W2.2 真实 OCR 矩阵

至少 8 张输入 × 3 个引擎/模式 × 2 个开关（默认/legacy）：

- 受控英文三行段落、受控段落+4 标签、中文设置页、真实 4K 截图；
- 密集多栏文本、日文假名段落、中英混排、小字号/低对比度各 1 张；
- 引擎：OnnxGpu、OnnxCpu、WindowsOcr（本机语言包不可用时记“未判”，不冒充通过）；
- 语言：`zh-en`、`ja`、`ko`（按模型/语言包能力记录）。

每张记录：
`LINES`、`CJK\s+CJK`、`TEXT_EQ_LINES`、`GEOMETRY_BAD`、`PARAGRAPH_GROUPS`、单字符行占比、耗时、峰值内存、异常/空结果。

**重点不是只看“通过”，而是看行数变化是否合理**：同一段落不能被切碎；不同窗口/列不能被旧实现式误并。

#### W2.3 性能/资源

- 4K 截图冷/热各 5 次，记录 p50/p95、首行延迟、总耗时、峰值工作集。
- 1000/5000 个合成 fragment 的 composer 压力测试，记录耗时曲线；确认 `MergeOrphans` 不会进入不可接受的多轮。
- OCR 连续触发 10 次，观察模型会话、线程、内存是否回收；与 0.3.20 基线对照（只看同一台机器、同一电源模式）。
- 取消：推理/批处理中取消，确认 `OperationCanceledException` 传播、不产生半截结果、不吞异常。

### W3 — 可靠性与隐私/安全审查

- 空/异常输入：null `Text`、空 `Words`、零尺寸、超长文本、换行、控制字符、重复框。
- 模型/运行环境：模型缺失、字典缺失、`numClasses` 不符、DirectML 不可用回 CPU、Windows 语言包缺失。
- 并发：两个 OCR 同时触发、取消一个、模型卸载与重建（只审交互，不重写未改动逻辑）。
- 诊断开关：`TTC_OCR_DUMP_BOXES=1` 的落盘路径、权限、文件名冲突、文本敏感性、清理策略；评估是否需要“仅在显式诊断模式/脱敏/保留期限”。
- 日志：新日志是否含完整 OCR 文本、用户路径、模型路径；检查 `CoreLog` 级别。
- 回退开关：`TTC_OCR_LEGACY_LINE_MERGE=1` 时 Text/Lines/预览/翻译是否仍一致；legacy 是否仍会写空格（文档是否说清）。

### W4 — 当前软件可用性（真包 + 真 UI）

1. 解包/安装 0.3.20 7z 或 MSIX，确认版本 `0.3.20.0`、可启动、OCR 预览可用。
2. 对同一张图分别跑：
   - 0.3.20 包（旧二进制）；
   - HEAD 构建（新二进制）。
   对比 OCR 行文本、预览行数、复制全文、翻译段落组、耗时。
3. 真实 UI 走查：截图→OCR→预览→复制全文→翻译→关闭；检查：
   - 预览覆盖不盖字/不越界；
   - 复制文本与预览同序；
   - 段落分组不把独立标签并进段落；
   - 错误/空结果有明确提示；
   - 4K 下不卡死、不闪退。
4. **明确回答**：用户现在装 0.3.20 能不能用？修复是否可见？如果不可见，属于发布缺口还是代码缺陷。

### W5 — 发布完整性

- 证明 0.3.20 MSIX/7z 与 `ec440aa` 的对应关系（版本、文件哈希、构建日志）；如果无法证明，记“provenance 未证实”。
- 对比包内 `TrueToneCap.Core.dll` 与 HEAD 构建哈希，确认 OCR 修复是否在包内（预期：不在）。
- 检查 `Package.appxmanifest` 版本、签名、依赖、架构、MSIX 内容清单、7z 内容。
- 检查 `CHANGELOG` 的“未发布”条目与版本号是否一致；`v0.3.20` tag 缺失是否影响回滚/发布追踪。
