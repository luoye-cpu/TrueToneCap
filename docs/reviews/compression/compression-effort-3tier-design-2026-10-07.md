# 设计：压缩强度三档（AVIF / JPEG XL / WebP）—— 已实现

> 需求（用户 2026-10-07）：给 AVIF、JPEG XL、WebP 各加**一栏「压缩强度」三档** ——
> 一档最慢体积最小、一档中间、一档较快体积也可接受。JPEG LI 与 PNG 不加。
> 默认档 = 「均衡」，并**顺带把 JPEG XL 从 `-e 9` 提速**。
>
> **状态：已实现并验证**（构建 0 警告 0 错误；7 套件 1796 通过 / 0 失败）。

---

## 0. 最终取值与实测（4K 真实截图）

样张 `z0_138272.png`（3.6 MB），`-d 1.0` / `-q 60`：

| 格式 | 最小体积 | 均衡（默认） | 最快 |
|---|---|---|---|
| **JPEG XL** | `-e 7` → 0.51 s / **255.2 KB** | `-e 5` → 0.31 s / **253.7 KB** | `-e 3` → 0.26 s / **258.8 KB** |
| **AVIF**（软件） | `-s 2` → 5.44 s / **110.7 KB** | `-s 6` → 0.39 s / **123.4 KB** | `-s 10` → 0.19 s / **148.8 KB** |
| **AVIF**（NVENC） | P7 | P4 | P1 |
| **WebP** | `-m 6` → 0.95 s / **248.3 KB** | `-m 4` → 0.74 s / **258.2 KB** | `-m 2` → 0.42 s / **267.8 KB** |

三档都产生了**单调且有意义**的取舍（AVIF 最明显：时间 28×、体积差 34%）。

⚠ **JPEG XL 这张样张上三档体积几乎相同（255 / 254 / 259 KB）** —— 这是实话，不是没接线。
JXL 的 effort 在 3..7 区间对这类内容本来就是"时间不同、体积接近"；把它当"省体积的旋钮"
会失望，它的价值是**在几乎不损失体积的前提下把 25 秒降到 0.3 秒**。

## 1. 为什么是这三个格式

只有它们**有独立的 effort/speed 旋钮**，且当前都在代码里**硬编码**：

| 格式 | 现状（硬编码） | 可用范围 |
|---|---|---|
| AVIF（avifenc 软件） | `-s 6`（`NativeAvifEncoder.cs` 注释里写着"6 是甜点档"） | `-s 0..10`（0 最慢） |
| AVIF（NVENC 硬件） | `PresetP1`（`NvEncoderNative.cs`） | P1..P7（P1 最快） |
| JPEG XL | `-e 9`（三处） | `-e 1..10`（默认 7） |
| WebP | **未传** `-m`（cwebp 默认 4） | `-m 0..6`（6 最慢） |

**JPEG LI / PNG 为什么不加**：它们的"压缩强度"与**质量**是同一个旋钮（JPEG LI 是 butteraugli 距离、
PNG 是无损压缩级别），加三档等于**再开一个质量入口**，与现有质量滑块打架；且 PNG 无损，
"更慢更小"只有一个方向。用户需求里也说它们"速度都是最慢但体积最小" —— 即**当作已固定**。

## 2. 实测数据（4K 真实截图，`TrueToneCap_20260930_025449195.png` 4.66 MB）

### JPEG XL（`cjxl -d 1.0`）

| effort | 时间 | 体积 |
|---|---|---|
| 1 | 0.65 s | 1564 KB |
| **3** | **0.64 s** | **490 KB** |
| 5 | 0.82 s | 491 KB |
| **7** | **1.09 s** | **490.8 KB** |
| 9（现值） | **25.00 s** | **541.3 KB** |
| 10 | 24.04 s | 540.9 KB |

⚠ **重要异常**：在**这张**样张上，`e9/e10` 比 `e3` **慢 39× 且体积大 10%** —— 即 effort 9/10 是**严格更差**的。
另一张样张（`z0_138272.png`）上 e9 比 e7 小 5.4%，所以**不是普遍更差，但不稳定**。

⇒ **三档只能落在 e3 / e5 / e7 附近**；把 e9 设成"最高档"会给出"更慢且更大"的档位，那是骗人。

### AVIF（`avifenc -q 60 --codec aom`）

| speed | 时间 | 体积 |
|---|---|---|
| 0 | 8.46 s | 127 KB |
| 2 | 5.71 s | 128.5 KB |
| 4 | 2.79 s | 134.4 KB |
| **6** | **0.94 s** | **144.3 KB** |
| 8 | 0.61 s | 157.3 KB |
| 10 | 0.59 s | 180.1 KB |

**单调、干净**（speed 越小越慢越小）。适合做三档。

### WebP（`cwebp -q 90`）

| method | 时间 | 体积 |
|---|---|---|
| 0 | 0.39 s | 305.9 KB |
| 2 | 0.42 s | 267.8 KB |
| **4** | **0.74 s** | **258.2 KB** |
| 6 | 0.95 s | 248.3 KB |

**单调**，但**总差异很小**（0.39→0.95 s、306→248 KB）—— WebP 的 method 影响远小于另两个。
三档仍可给，但收益有限（如实标注）。

## 3. 三档取值（依据上表）

| 格式 | 档 1「最小体积」 | 档 2「均衡」（默认） | 档 3「最快」 |
|---|---|---|---|
| **JPEG XL** | `-e 7`（1.09 s / 490.8 KB） | `-e 5`（0.82 s / 491 KB） | `-e 3`（0.64 s / 490 KB） |
| **AVIF**（avifenc 软件） | `-s 2`（5.71 s / 128.5 KB） | `-s 6`（0.94 s / 144.3 KB） | `-s 10`（0.59 s / 180.1 KB） |
| **AVIF**（NVENC 硬件） | P7 | P4 | P1 |
| **WebP** | `-m 6`（0.95 s / 248.3 KB） | `-m 4`（0.74 s / 258.2 KB） | `-m 2`（0.42 s / 267.8 KB） |

⚠ **默认档的"提速"效果**：JPEG XL 从 `-e 9`（25 s）换成 `-e 5`（0.82 s）＝ **30× 提速**，
体积在同一张样张上**几乎不变**（540.9 → 491 KB，反而更小）。这正是用户要的"顺带提速"。

⚠ **AVIF 缺省档位的取舍**：现状是 `-s 6`（0.94 s/144 KB），与"均衡"一致 ⇒ **AVIF 默认行为不变**。
若把均衡设成 `-s 4`（2.79 s/134 KB）会更小但慢 3 倍 —— **不采用**，因为默认档不该显著变慢。

## 5. 风险与判据

1. **默认行为改变**（JPEG XL 25 s → 0.82 s，体积 ±10%）：这是用户明确要的，但**必须写进 CHANGELOG**。
2. **AVIF 硬件 vs 软件档位不对等**：NVENC 只有 P1..P7，与 avifenc 的 0..10 不是同一把尺。
   需要一组显式映射，并**在注释里说明两者不可比**（否则后人会以为"同一个档应该一样快"）。
3. **判据怎么做**：档位→命令行参数的映射要能被单测钉住（照本仓既有做法：用源码字符串锁
   + 行为断言），否则"改了档位没生效"这类问题看不出来。
4. **WebP 收益有限**：如实标注，不夸大。
