## 🔴 最重要发现：F4 静置测量前提失效，"0.447 帧/s"不成立

**这是本次审查唯一推翻交接文档结论的点。**

### 证据链（全部出自 `tests/output/f45-meters-cell.log` 原始时间戳）

| 时刻 | 事件 | 来源行 |
|------|------|--------|
| 14:17:51.084 | 选区截图启动（热键生效） | :29 |
| 14:17:51.473 | 渲染帧 #1 | :15 |
| 14:17:51.540 | 脚本开始静置 45s | :10 |
| **14:17:56.223** | **"选区完成 1477x1004 @(窗口内 1178,536)"** ← 静置期间不该发生 | :31 |
| 14:17:56.484 | 渲染帧 #21 | :17 |
| 14:17:56.499 | **渲染循环退出，总帧数=21** | :18 |
| 14:17:56.510 | **窗口关闭** | :27 |
| 14:18:06.366 | WGC 空闲超时（预览窗已死 10s） | :22 |
| ~14:18:38 | 脚本静置计时结束（47.02s），Esc 打在已关闭的窗上 | :11-12 |

- 21 帧的打点（每 10 帧一行）**全部落在 5.011s 内**（行 34 自证："跨 20 帧用 5011ms"），不是分布在 47s 静置段上。
- "选区完成 1477x1004"来自 `HdrCaptureWindow.cs` 的**单击选窗路径**（:3526-3548：无拖动 → 优先选中悬停窗口）——即静置期间有一颗**脚本外的鼠标左键释放**落进预览窗（脚本全程零注入；脚本 13:26 跑过 select 臂后光标停在桌面，14:17 时段物理输入干扰是最合理解释）。
- 于是：预览窗在静置开始 **4.96s** 后关闭，之后 ~42s 测的是**没有预览窗的进程空转**。

### 结论

- 交接文档的"静置 47.02s 内渲染 21 帧 ⇒ 0.447 帧/s（超理论 33%）""83.01ms/拍"**全部无效**：分子是 5.4s 窗生命周期的帧数，分母是 47s 无窗墙钟，"静置唤醒比预期频繁 33%"的解读不成立。
- 不受影响的部分：**"每 3s 定时器醒一次并无条件 RequestRedraw"的机制本身是代码事实**（`HdrCaptureWindow.cs:4310-4332`，每次回调置 `_mIdleWakePending` + `RequestRedraw()`，且 WGC `FrameArrived` 不触发预览重绘——静置时该定时器是画面跟随桌面内容的唯一路径）。静置唤醒**存在**，但其幅度从未被有效测量。
- 交接文档"RenderCore vs 进程总开销需分离"的实际状态：**渲染段口径的仪表已经存在**（`RenderLoop` 只圈 `RenderCore()` 的 `_mFrameUs`、静置帧独立桶 `_mIdleWakeUs`，`HdrCaptureWindow.cs:968-975`；Close 时 `DumpPreviewMeters` 输出 `[Meter/F4]` 结算行含静置帧合计/峰与 EnumWindows 合计）。缺的只是脚本把它摘出来——14:17 轮的 `[Meter/F4]` 行在日志里但未被摘录。

### 已落地的修正（本次审查）

1. **`tests/manual/safety/f45-meters-cell.ps1` 加前提守卫**：
   - 静置前光标钉 (10,10)、结束后 `GetCursorPos` 对账（物理输入干扰显式告警）；
   - 静置中每 4s 确认 TTC_HC 预览窗存活，提前消失立即停表标记失效；
   - 读数前裁决：静置臂出现"选区完成"行、或渲染循环退出/窗口关闭早于静置结束 ⇒ 宣布"测量失效"，**不出帧率/每拍 CPU 数**，RC=1；
   - 摘录补 `[Meter/F4]` 结算行，读数区新增"渲染段（RenderCore）vs 整进程 CPU"两口径对照——交接文档待办"RenderCore vs 进程总开销分离"由这两行并列落地。
   - ⚠ 脚本改动**未经运行验证**（本会话 pwsh 不可用），首次复测时注意观察语法。
2. **F4 复测待办**：排除物理干扰（无人为操作时段或锁输入）重跑 `-IdleSec 45`，预期拿到有效的静置帧率与两口径 CPU 对照；之后才轮到"是否延长静置间隔/跳过无变化重绘"的产品决策。

## 🟡 PQ 查表：高可信，备忘纠错

- 实现 4 条全部属实（4096 段 s=L^(1/4) 表、两次 sqrt+线性插值、EncodeExact 对照臂 + `TTC_PQ_TABLE=0` 回退、≤12-bit 表/>12-bit 原式，调用链两点核实）；线程安全由静态只读字段初始化器（CLR cctor）保证；越界性经 float 逐级推导不可达；精度锁（10/12-bit ≤1 码、64 格弱表正控、16-bit 全等）齐备。
- **数学纠错（备忘错、代码对）**：代码常数与 BT.2100 Table 5 一致（c1=3424/4096=107/128、c2=2413/128、c3=2392/128）；审查任务曾用"107/16384"一组（漏 ×32）是错组——按它 100 nits 会算出 ~1e-52。代码抽查 PQ(100 nits)=0.5081 ✓。
- 小风险（不阻断）：测试⑤"两臂不同"被零点吃满（PQ(0) 极限 7.3e-7），假表也能过⑤，真防线是③+①；NaN 输入在表臂会抛下标越界（低危）；`SegmentsCount` 属性零引用（死代码）；性能读数（58.4/134.6ms）只能文档自洽，本会话不可复测。

## 🟡 双屏 #46：声明高可信，三处表述修正

| 交接文档 | 实际 |
|---------|------|
| "_iccCache 按 HMonitor 键" | 键 = **设备名#物理指纹**（EDID CRC32→PnP ID→设备名三级回退），HMONITOR 只用于派生——防同名不同物理显示器错缓存（`ColorProfileProvider.cs:16-29`） |
| "每屏 Float16/BGRA8 独立缓存，双 4K ~264MB" | HDR 成功时托管堆估算 **~863MB**（HDR 会话双 float[] 缓冲各 132.7MB + 画布 265.4MB…）；~264MB 只对得上无 HDR 口径。缓解：15s 空闲清池（`IdleStopDelayMs`），非常驻 |
| "会话创建延迟累加" | 仅**冷路径**成立（`session.Start()` 在 `_poolLock` 内 → N 屏串行建）；暖路径 TryGetValue 复用零创建成本 |
| "虚拟坐标转换整数溢出风险未防护" | 形式上无 checked，但需 >536.9M 像素（≈124 块 4K）才溢出，不可达；且回绕后 `new byte[负数]` **响亮失败**而非静默损坏。拼接是**包围盒公式**（Min/Max），对负坐标正确 |

- 附带核实：多屏 HDR 不是"每屏一条"——只选一个 hdrSource 建**一条** Float16 会话（一张图只能一种色彩空间，:2433-2453）；会话池键 `(HMONITOR, IsHdr)` 隔离、无 GetOrAdd 竞态、并发截图被 `s_captureLock` 拒绝重入。
- 双屏专项性能测试仍受硬件限制（单屏环境），交接文档的"等设备"判断维持。
