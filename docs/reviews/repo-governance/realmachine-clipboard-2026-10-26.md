| 层 | 内容 | 结果 |
|---|---|---|

## 1. 过程中修掉的两个夹具缺口（W1a 格）

1. **OutputPath 键缺失即拒绝跑**：差量写盘 ⇒ 设置文件用默认输出目录时这个键根本不写
   （本机实测：顶层只有 5 个键、OutputPath/FormatIndex 双缺）。夹具原先锚点命中 0 次就
   RC=2 未判。改为与 FormatIndex 同一规矩：0 次合法，走"插在首个 `{` 之后"的补键路，
   写入按 JSON 转义反斜杠（首版补丁误写四道 `\`，靠 Windows 路径容错侥幸能用，已改回两道）。
2. 顺带核对：`Set-Settings` 的 FormatIndex 缺失补键路本就存在，两条路径形状现在一致。

## 2. 剪贴板"参数错误"取证（本轮真发现）

首趟 W1a（**提权**环境跑的——本会话本身是管理员，应用继承）：
捕获/编码/落盘全绿，但应用日志 `复制到剪贴板失败: 参数错误。`，剪贴板回读全空。
应用自己也在启动时告警了 `检测到以管理员权限运行`。

**隔离探针**（普通 5.1 STA 进程，逐调用拆解）证明：提权下
`GetFileFromPathAsync` / `SetBitmap` / `SetContent` / `Flush` 照常可用，位图能进剪贴板。
旧代码日志形状（无"位图通道不可用"内层警告 + 外层参数错误）⇒ 抛错点在最后的
`SetContent`（位图+存储项组合包在提权会话里被拒；可能是编组顺序因素，也可能有瞬时争用，
单样本无法进一步区分 —— 诚实记录）。

**产品加固**（MainWindow.CopyFileToClipboardAsync）：位图通道提前到第一位、
两个通道各自 try/catch 独立降级 —— 任一通道成功就 `SetContent`，状态栏如实报告
"仅位图/仅文件"；两个通道都失败才空手而归。改动后双轮复测：

| 运行上下文 | 代码 | 判据 |
|---|---|---|
| 普通权限（runas /trustlevel:0x20000 降权） | 新 | **判词 OK**，剪贴板 位图 3840×2160 + 文件=1 |
| 提权（管理员） | 新 | **判词 OK**，同上 —— 双通道都在，无失败行 |
| 提权 | 旧（对照，历史现场） | 剪贴板全空，`参数错误` |

用户平时双击启动是普通权限，本就完全不受影响；加固后提权用户也不再因单通道失败
丢掉整个剪贴板。
