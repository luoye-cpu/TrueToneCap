# OCR 预览字号「非常小」根因闭环 + HDR 选区回读失败 — 实机排查（2026-11-11）

用户口径：「OCR 后的字体非常非常非常小，完全看不清楚，至少应该不比原有的字体小吧？
这个问题修了 N 次了」—— 要求实机测试对比字高来修，不许只读代码。

本文是本轮的完整证据链与修复记录。前置的 2026-11-09 那轮
（`OCR-Translation-FontSize-Issue-Fix-2026-11-09.md`，FitFontSize floor=0.65×框高）
没有治住症状，原因在下文 §2 —— 不是那轮的判据写错，是锚本身错了。

---

## 1. 排查方法（实机台架）

- 底图窗：全屏白底 WinForms 窗（TopMost），画两行**已知像素高**的黑字：
  `OCR SIZE CHECK 123456`，Consolas Bold **40px**（实测墨高 26px）与 **20px**（墨高 13px），
  `GraphicsUnit.Pixel` 保证 1:1 物理像素。位置避开 MSI Afterburner 的 GPU 监控 HUD（屏幕左上角会压字）。
- 热键注入：`keybd_event` 发 Ctrl+Shift+S（托盘截图热键）→ `SetCursorPos`+`mouse_event`
  拖拽选区 (40,400)→(900,650)（尺寸徽标实测 860×250，与拖拽 1:1 ✓）→ 点工具栏「识字」。
- 预览窗：Win32 类 `WinUIDesktopWin32WindowClass`，标题 `TrueToneCap 文字识别`，
  实测 (1450,859)-(2390,1229)。FindWindowW 精确匹配在本轮不稳，改用 EnumWindows+GetWindowTextW 轮询。
- 测量：CopyFromScreen 截图后逐行暗像素/亮度直方图统计（PowerShell System.Drawing）。
- 台架残留在 `%TEMP%\ttc_ocr_font`（临时目录，可随时删）。

⚠️ 两个环境坑，都是本轮真踩：
1. **Debug 版的设置文件在 exe 旁**（`bin\...\win-x64\TrueToneCap.settings.json`，便携布局），
   不是 `%LOCALAPPDATA%\TrueToneCap\`——后者属于另一套安装版实例。写错文件=设置"不生效"。
   bash `printf` 写 JSON 会吃掉 `\\` 变无效转义，得用 Write 工具写精确字节。
2. 日志详细度档位存 settings（`LogVerbosity`：Brief/Diagnose/Trace），**回读排障必须切 Diagnose**
   ——WgcCaptureService 的 `[Pool]` 日志全是 Debug 级，Brief 档下一个字都没有。

## 2. 字号根因链（全部有实测数字）

### 2.1 第一层：det 检测框高度系统性缩水（≈0.6×真实字高）

`--ocr-dump` 探针（本轮新增，`dotnet run --project src/TrueToneCap.Tools -- --ocr-dump <png> <x> <y> <w> <h> <modelDir> gpu`）
对 860×250 捕获区跑生产同路引擎（PP-OCRv6 DirectML FP16，en-US）：

| 文本 | 真实墨高 | det 框高 | 缩水比 |
|---|---|---|---|
| "OCR"（40px 行单词） | 26px | 16px | 0.62 |
| "0CRSIZECHECK123456"（20px 整行） | 13px | 8px | 0.62 |

DBNet 系检测框在截图上把字高削到 ~0.6 倍；20px 行的框甚至把识别文本劣化成
无空格 + O→0（`0CRSIZECHECK123456`）。

### 2.2 第二层：字号锚 = 0.65×框高 ⇒ 覆盖字恒为原字的 4~6 成

FitFontSize 旧口径 `startPx = 0.65×框高`：40px 行单词框 (0.65×24=15.6) → 覆盖字 ~11.5 物理px，
**原字 26px 的 44%**；20px 行 floor(12) → ~8.7 物理px，**原字 13px 的 67%**。
2026-11-09 的修复（floor=max(12, 0.65×框高)）方向对、锚错 —— 锚本身缩水 0.6 倍，
floor 再准也只到原字的六成。

### 2.3 第三层：覆盖字固定白色 (240,240,240) 在浅底上隐形

原文高亮模式的块底 = 图像经半透明蓝芯片（α80, RGB(56,120,210)）合成，浅色截图上有效底亮度
~136-210；白字对 160 灰底对比度 ~1.6:1。亮度直方图实测：上行 4 个芯片内**一块白色覆盖字像素都没有**
（RGB(224,224,224) 桶 0%），下行仅 4.9%（叠在原字深色墨上才勉强可见）。
芯片里"看到的小字"其实是**原图透出来被染蓝的墨**（RGB(32,32,64)），不是覆盖字。

### 2.4 附带：det 把 40px 行拆成 4 个词框 ⇒ 「5 行」

det 对大间距大字号文本按词出框（1 词 1 框 1"行"），预览"一行一块"跟着碎成词芯片。
本轮**不修**（见 §5 遗留），字号新锚在词框粒度下同样成立（宽度锚按框内宽÷字符单位，
词框逐个验证误差 ±11% 且方向宁大勿小）。

## 3. 修复（三点）

1. **字号锚换成宽度反推**（`OcrTextOverlay.EstimateOriginalFontPx`）：
   `em ≈ (框内宽) ÷ Σ(字符宽度单位)`，CJK/全角 1.0、其余 0.55、空白 0.5；
   荒谬值防护 `em ≤ 框高×2.6`。FitFontSize 的 `startPx` 语义改为"原字号估计"，
   floor = startPx —— 覆盖字 ≥ 原字（用户口径），译文放不下宁可折行溢出也不缩过原字号。
   预览（RenderOverlay）与导出（Compose，新增 `originalTexts` 参数）同锚，口径不漂。
2. **覆盖字对比色**（RenderOverlay）：原文模式按块底有效亮度选字色
   （`SampleBlockLuma` 隔行采样 `_rawPixels`，亮度 ≥136 用近黑 (20,20,20)，否则白）；
   译文模式块是深色不透明，恒白。
3. **台架先决 bug（HDR 选区回读失败）**：见 §4。

## 4. 先决 bug：15 秒空闲回收把冻结槽连根拔（路线 B-3 × ScheduleIdleStop 时序冲突）

实机第一轮点「翻译」直接 toast「❌ 截图失败」，预览窗根本不开。Diagnose 日志 +
`[Pool]` 探针（本轮给 ReadSharedRegion 两个静默 null 出口补了留痕）定位：

```
[Pool] 选区回读查无会话 key=(...,True) 池内:      ← 会话池是空的
[Pool] 选区 SDR 回读查无会话 key=(...,false) 池内: ← 空
```

`ScheduleIdleStop()`（WgcCaptureService.cs）在每次捕获结束挂 15s 定时器，到期
`Dispose()` 全部会话并清池。路线 B-3（2026-10-30）把选区像素回读推迟到**用户点完工具栏**
—— 选区窗开着超过 15s（人在框选/选按钮，实测两次分别是 17s/19s，Meter/F5 结算行恒在
捕获后 15s 整出现）会话就没了，回读必挂。旧注释"15 秒后 Dispose 与下游无关"只对
"像素已复制出会话"的旧路线成立；B-3 之后**冻结槽里的像素就是下游要交的货**。

修复：空闲回收到期时若仍有冻结槽被选区窗持有（`SharedHeld`），顺延一轮再查，
交还后才真正回收。复验：顺延触发 → 回读 19.6ms/7.2ms → OCR 成功 → 会话在交还后正常回收。

## 5. 复验数字（同一台架、同一流程）

| 项 | 修复前 | 修复后 |
|---|---|---|
| 40px 行覆盖字（预览内） | ~11.5px 白色（原字的 44%，且隐形） | **19px 深色（原字的 100%）** |
| 20px 行覆盖字（预览内） | ~8.7px 白色（原字的 67%，挤压） | **10px 深色（原字的 105%）** |
| 预览窗能否打开 | 15s 后动作必败「❌ 截图失败」 | 任意时长选区后正常打开 |
| 门禁 | — | 8 套件 2694 断言 0 失败，无未判格子 |

（"预览内原字" = 原字墨高 × 预览缩放 0.73：40px 行 26×0.73≈19、20px 行 13×0.73≈9.5。）

## 7. 第二轮（同日晚）：重影/能见度 —— §3② 的颜色修复没治住"字叠字"

用户拿**暗底浅字**内容（终端截图）实测后反馈「能见度仍然很低」。3× 放大用户截图：
覆盖字确实已是白色、字号也已对齐，但**原字完整透出**，与覆盖字错位叠成双影 ——
§3② 只把字色换成了对比色，块底仍是 α80（31% 不透明）半透明蓝，盖不住原字；
且 det 框高只有字高的 0.6 倍，**块比墨迹还矮**，原字上下探出块外。
浅底黑字内容下双影被"深色叠深色"部分掩盖（第一轮台架没抓到），暗底内容彻底暴露。

修复（预览 + 导出同口径）：

1. **块扩到罩住墨迹**（`OcrTextOverlay.ExpandRectToInk`）：竖向扩到 1.45×估计原字号
   （单行高），横向扩到排版宽×1.10 + 行内留白（10% 余量防 ±1px 排版差触发折行——
   第一版零余量在暗底台架上立刻抓到 "OC/R"、"SIZ/E" 折行堆叠），中心不动。
2. **块底垫色**（`MedianBlockColor`）：取块区域逐通道**中位数**（字迹占比 <50% 时中位数即
   背景色）作垫底色 —— 原字被干净盖掉，块色随底图融入（纯色背景上不可见）。
   预览侧按整窗暗化折算（darkOverlay α90 黑 ⇒ ×165/255）后呈现，块与周边亮度一致。
3. **字色按垫底色取对比**：垫底亮度 ≥136 用近黑，否则白。Compose（导出）同法：
   垫 FillRect 后画字 —— "预览所见 = 产物"契约保持。
4. **原文模式禁折行**（TextWrapping.NoWrap）：显示文本就是块内原字，锚定字号下单行放下；
   译文模式保留折行（译文更长是设计行为）。

## 8. 第三轮（同日夜）：框不够大裁字 + 词碎片化 —— 块尺寸从"拍估计"改"实测"

用户实测反馈「框不够大导致文字被截断」（截图：词芯片 "OCl"/"CHEC!" 末字符被裁）。
三个连环根因，全部实机复现：

1. **块宽是估计值**：宽度单位（拉丁 0.55em）低估用户真实字体的字幅（中文字体渲染拉丁文
   更宽），锚定字号下末字符越过块边被裁。修复：**XAML Measure 实测定块** —— 先排版
   TextBlock 量 DesiredSize，块 = max(墨迹覆盖估计, 文字实测)+边框；导出侧同理用
   `RasterizeText` 返回的真实字形尺寸扩块（先光栅化→扩块→采样垫底→画字，顺序不能乱，
   垫底若在扩块前画，扩出条带无垫底 = 重影回流）。块位置保持墨迹块中心、收拢进画布。
2. **det 框横向也缩水（~0.92×）+ 词框相邻（间隙可低至 2px）**：任何按词框的横向扩块/
   墨迹扫描都会跨进邻词 ⇒ 芯片互相重叠、后画的块盖住先画块的字尾（实机 3× 放大抓到）。
   修复：**引擎层 det 框合并成视觉行**（`OnnxOcrEngine.MergeDetLines`：垂直中心落在簇的
   垂直范围内即同簇，簇内按 X 排序、文本空格连接、行框取并集）—— 行间只有行距，几何
   操作天然安全；顺带治好「5 行」虚报（40px 行 4 词 4 框），状态栏恢复真实行数（2 行）。
   zh-en 混合路的行重建（OcrService）早有同型先例，onnx 单语路此补齐。
3. **垫底 α245 仍有 3.9% 透出**：平坦底上 6 luma 的残影肉眼可辨（实测 (510,145)=154 =
   0.961×160 的理论 bleed 值）。修复：**全不透明 α255** + 暗化补偿系数精确化
   （160/255 → 165/255 = (255-90)/255，块底与周边逐值一致）。

复验（白底台架 = 用户同场景）：**"OCR SIZE CHECK 123456" / "0CRSIZECHECK123456"
两行芯片、零截断、零残影、块底与底图无缝；状态栏「2 行」正确；10 套件 --all 全绿。**

## 6. 遗留与后续

- **det 词框拆行**（§2.4）：「N 行」计数与词芯片化。合并需要按垂直重叠+X 间距把 det 框聚成
  视觉行（zh-en 混合路已有同类逻辑 `MergeOverlappingWords`/行重建，en 单语路没有）；
  动它会改 Lines 契约（翻译快照按行对齐），本轮不动，字号锚已不依赖行合并。
- **det 框高缩水**：若未来有"按框高锚"的新调用点，记住先核 det 框高再设计；
  宽度锚（EstimateOriginalFontPx）是当前唯一经过实机校准的字号来源。
- native 工具（avifenc/cjxl 等）内嵌解压偶发被 360 主动防御拦成"不可用"，门禁表现为
  usability 套件 4 条 Skip —— 重跑即恢复（本轮实际发生一次），不是代码回归。
